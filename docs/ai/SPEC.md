- 関係する文書：設計の意図と決定事項は [DESIGN.md](DESIGN.md)。本書は**いま実装されている挙動**と、設計書との差分をまとめる。

## 1. 概要

- ブラウザだけで動く 1 ページのゲーム。`index.html` を開くと遊べる（サーバー・ビルド・外部ライブラリなし。`file://` で動作）。
- 画面は DOM で構成（canvas は使わない）。文章を読み、伏せ字を追い、メモを取るゲームのため。
- シナリオはシード値から決定的に生成される（`index.html?seed=123`）。LLM による文章化を除き、同じシードからは同じシナリオになる。
- 論理層（真相・手がかり事実・検証）はすべて JavaScript で実装。物語層（主観ログの文章）はテンプレートで作り、OpenAI API が設定されていれば LLM で書き直す。
- ログを書く前に「物語の正本」（場面の時系列：いつ・どこで・誰がいて・何が起きたか、と因果のつながり）を作る。主観ログの各エントリはどれか一つの場面に属し、書き手が見聞きした出来事だけを書く。
- 住人ごとに人物設定（性別・年齢・性格・文化への態度・持続的な特徴など）を、シェルターごとに文化（区画の性格・目印・序列の習慣・偏見）をランダムに作る。
- **主観ログには答え（区画・入居順・職能）を書かない。** 人物や文化がにじむ観察だけを置き、プレイヤーは素性の分かった住人の描写を例にして文化の決まりごとを見つけ、それを当てはめて身元を推理する。文化のルールはどの資料にも一般論として書かない。

## 4. 生成パイプライン（`generator.js`）

`Generator.generate(seed)` は最大 40 回試行する。試行 *n* は `mixSeed(seed, n)` の乱数系列で最初から組み立て、検証器（§6）を通ったら返す。通らなければ例外。

```
[1] 住人 → [2] 関係 → [3] 事件 → トリック適用 → 整合性回復 → [4] 状態と安全判定
→ [6] 解錠グラフ（ID の手がかり配置）＋到達可能性 → [5] 物語の正本と各エントリ（story.js）
→ [8] テンプレート文章化 → [9] JSON 組み立て → [7] 検証
```

### 4.1 [1] 住人

| 項目 | 値 |
|---|---|
| 人数 | 12〜16 |
| 区画 | 3〜4（A〜D）。各区画に最低2人 |
| 相談役（51） | 2〜3 人 |
| 入居番号 | 1〜`max_entry`。`max_entry = 人数 + 欠番(0〜2)`。最大値は必ず現住人が持つ |
| 職能 | 重み付き抽選。記録係（52）は最大1人。外部偵察（42）が居なければ 70% で1人置き換える |
| ID | `区画-入居順2桁-職能コード`（例 `C-07-31`） |
| 名前 | 姓（漢字）＋名（カタカナ）。重複なし |
| 伏せ字トークン | 紛らわしい文字を除いた4文字の英数字。重複なし |
| 語り口 | 一人称（私・俺・僕…の重み付き）、口癖（住人ごとに一意）、文末の癖（plain / ellipsis / exclaim）、性格、年齢 |

### 4.2 [2] 関係

人数×0.7 組。種類と重み：家族20・友人30・恋人15・対立25・師弟10。恋人と対立は 40% の確率で管理AIが把握（`known_to_ai`）。
用途は二つ：主観ログの描写（日常エントリ）と、殺人の加害者選び（対立相手を優先）。

### 4.3 [3] 事件

**時間軸**（時刻は D01 00:00 起点の分で持つ）

- 最後の死亡日 `last_death_day`：7〜21
- 異変の始まり `crisis_day`：3〜4（異変前の日常を2日以上とるため）
- 現在 `now_day`：最後の死亡日＋2〜4
- 死亡日は `crisis_day+1`〜`last_death_day`。必ず1人は最後の死亡日に死ぬ。

**生存者数**：0人 60% / 1人 30% / 2人 10%。生存者以外は全員死ぬ。

**危機の種類と死因の分布**（最初の死者は主死因）

| 危機 | 重み | 主死因 | 死因の分布 |
|---|---|---|---|
| outbreak 感染症の流行 | 25 | 感染症 | 感染症70・殺人15・事故15 |
| famine 食料の枯渇 | 25 | 飢餓 | 飢餓65・殺人20・事故15 |
| leak 放射能汚染 | 20 | 被曝 | 被曝70・事故20・殺人10 |
| strife 内部抗争 | 30 | 殺人 | 殺人70・事故30 |

殺人の加害者は、その時刻に行動できる住人から選ぶ（既存の加害者を 60%、対立相手を 60% で優先）。候補が居なければ死因を変える。
殺人の被害者が最期に加害者を見ている確率は 65%（見ていなければ目撃者が必要）。

### 4.4 トリック（`tricks.js`）

適用数：0個 20% / 1個 45% / 2個 35%。ランダムに選び、`order` 順に適用する。適用できなければ次の候補を試す。
各適用の後に整合性回復（死者・移植後の加害者は以後犯行できない等）を行う。プラグインは `A.Tricks.register({id, name, order, apply(ctx)})` で追加でき、`apply` は真相を書き換えて適用記録を返す（不可なら `null`）。

| # | id | 内容（実装） | 生成される手がかり | 判定への影響 |
|---|---|---|---|---|
| 1 | `chip_transplant` | 生存者 K が死者 V を殺害し、V のチップを自分に移植。K のログはチップ摘出の場面で途切れ、管理AIは K の信号途絶を報告。V のログは V の死の場面の後も K の語り口（一人称・口癖・仕事）で現在まで続く。V と K の一人称は必ず異なる | `STYLE_SHIFT`、V の最期の `KILLED_BY`、K の遺体が見つからない描写 | K（加害者）が生存 → 危険（潜伏者） |
| 2 | `log_tamper` | 相談役 C が V の最期の記録2件を削除させ、死因を「事故」と記録させる。真の死因は、非 outbreak なら 50% で感染症（隠蔽）、それ以外は殺人（加害者は C か別人） | 会話ログの `LOG_DELETED`・`DEATH_CLAIM`、目撃者ログの `DEATH_SIGN`（＋殺人なら `KILLED_BY`） | 隠された感染症なら危険（感染） |
| 3 | `misperception` | 暗闇での殺人。目撃者 W が無関係の X を犯人と思い込む | W のログに `KILLED_BY`（certainty=low）。被害者の最期には声による確かな `KILLED_BY` | なし（取り違えを誘う） |
| 4 | `unrecorded_person` | チップを持たない侵入者が、時間的に連続する1〜3人を殺害。被害者の死因は `cause: 'intruder'`、`killer: null`（侵入者は住人 ID を持たない）。50% でまだ中に居る | 被害者の最期・目撃の `DEATH_SIGN`（見知らぬ人物の刃物・銃創・ガスマスクの人影。どれも「住人ではない者」と読める）、外部ハッチ記録の認証なし開放 | 中に残っていれば危険（侵入者） |
| 5 | `death_disguise` | 殺人を事故（または非 outbreak なら 50% で感染症）と偽る。相談役が居れば会話ログで、居なければ加害者が住人に吹聴（伝聞として別住人のログに残る） | `DEATH_CLAIM`（certainty=claim）。被害者の最期は殺人の感覚 | 偽装を信じると判定を誤る |

死因の語彙は全体で統一する：`murder` は住人が加害者の死だけ（`killer` は住人 ID）、`intruder` は侵入者による死（`killer: null`）、それ以外の死因に加害者は付かない。生成器・徴候表・検証器・往復検証のプロンプト・最終回答の選択肢・結果画面で同じ語彙を使う。生成時に不変条件として検査する（§6.4）。

### 4.5 [4] 現在の状態と安全判定

- 物資：飢餓死があれば `depleted`。なければ famine は `low`、それ以外は `low` か `sufficient`。
- 判定理由（この順で列挙）：生存者に殺人の加害者 →「潜伏者」、感染症死 →「感染」、被曝死 →「汚染」、侵入者が中に残る →「侵入者」。
- 結果：理由があれば `danger`。なければ飢餓死（物資枯渇）があれば `worthless`。どちらでもなければ `safe`。

### 4.6 [6] 解錠グラフ（ID の手がかり配置。改修仕様 v0.2 §6）

主観ログには答えの形の事実を置かず、観察事実（§5）だけを置く。プレイヤーが文化のルールを学習できるよう、既知の人物についての例（アンカー）を置いてから、未知の人物の観察を置く。

1. **番号の習慣の例**：相談役が自分の番号を書く（`OBS_NUMBER`、本人のログ）。相談役は2人以上いるので、最初から「番号＝入居順」を学習できる。
2. **段の作成**：相談役以外の住人を順に見て、2〜4人ずつ「段」にする。各人について次を置く（書き手はその段より前に既知の住人）。
   - 区画：次の3つの方法を順不同で試し、使えるものを使う。ルールは、仮のアンカーで学習できる（§6.2）ことを確かめてから正式に置く。
     - 身内の言葉：同じ区画の既知の書き手が「うちの区画の⟨p⟩」と書く（`OBS_INGROUP`）。ルールの例として、同じ区画の既知の二人の組を2組置く。
     - 区画の目印：既知の書き手が ⟨p⟩ の目印を書く（`OBS_MARKER`）。ルールの例として、その区画の既知の住人全員の目印を置く（本人の記述か他人の記述）。例の全員が別の属性値も共有していて紛らわしいときは使えない。
     - 区画の呼び名：区画外の既知の書き手が ⟨p⟩ を呼び名で呼ぶ（`OBS_OUTGROUP`）。例は区画の目印と同じ。
     - どれも使えない（最初の段など）ときだけ、既知の住人の少ない区画の人物を会話ログの直接の事実（`DISTRICT`）で特定させる（1シナリオ3件まで。一度に2人まで）。
   - 職能：既知の書き手が ⟨p⟩ の作業を見る（`OBS_WORK`。作業内容 ⇒ 職能は常識として扱う）。
   - 入居順：既知の書き手が ⟨p⟩ の番号を見る（`OBS_NUMBER`）。35% の確率で、順番の習慣の例を置いたうえで、入居順が ±1 の既知の二人に挟ませる（`OBS_AHEAD` などを2件。番号の差が2なので一意に決まる）。
3. **補助の観察**：住人の 60% に、それだけでは特定に至らない真実の観察を足す（職能分類の目印、序列の帯の目印、順番の習慣での前後）。
4. **検証**：ルールの学習を含む到達可能性を検証する（§6.2）。届かない住人がいれば、残りの会話ログの直接の事実で補って再検証（最大4回）。駄目ならこの試行は失敗。

### 4.7 [5] 物語の正本と各エントリ（`story.js`）

ログを書く前に、場面（scene）の時系列を作る。場面は「いつ・どこで・誰がいて・何が起きたか」と因果のつながりを持つ。

```js
{ id: 'S012', t, kind, title, place, district, dark,
  participants: [居合わせた住人], others: ['侵入者' など住人以外],
  events: [{ id: 'S012-e2', text: '{P:X}が…した', perceivers: 'all' | [住人], views: { 住人: その人の見え方 }, facts: [事実ID] }],
  causes: [先行する場面ID], facts: [この場面で生じる手がかり事実], details: [LLM が書き戻した細部] }
```

- **出来事の知覚**：`perceivers` がその出来事を見聞きした人物（`'all'` はその場の全員）。`views` は人物ごとの見え方（主観の誤認では「X だった気がする」）。各エントリには、書き手が知覚した出来事だけ（`perceived`）が渡る。
- **因果**：危機の場面は `発端 → 協議（会話ログ）→ 方針の決定（会話ログ）→ 食堂での告知 → 影響 → 口論` と連なる。死の場面はその時刻より前の最新の危機の場面を原因とする（時間が逆行しない）。発見・生体信号途絶の報告・改ざん・偽装・移植の場面は死の場面を原因とする。

**場面の種類**

| 区分 | kind | 内容 |
|---|---|---|
| 日常（D01〜`crisis_day−1`） | `meeting` / `work` / `queue` / `lunch` / `chat` / `meal` / `quarters` | 朝の会合／持ち場での作業／配給の列／食堂の昼食／通路での立ち話／食堂の夕食／夜の居住区（区画ごと） |
| 危機 | `onset` | 発端。outbreak は最初の発熱者が医務室へ、famine は水耕棚の根腐れ、leak は浄水室の線量計、strife は食堂での喧嘩（後の殺人の当事者か対立する二人） |
| | `consult` / `ai_report` | 相談役と管理AIの協議・方針の決定・削除や死因の記録の依頼／生体信号途絶の報告（会話ログに対応。主観ログは書かない） |
| | `assembly` | 相談役が住人を食堂に集めて方針を告げる（隔離・配給半減・給水停止・夜間外出禁止） |
| | `effect` | 方針の影響（区画の隔壁閉鎖、配給の列、照明の消灯など） |
| | `quarrel` | 危機をめぐる口論（後の殺人の当事者か対立する二人） |
| 死 | `death` | 死の場面。被害者・加害者・（襲撃の目撃者・誤認する目撃者）が居合わせる。時刻＝死亡時刻 |
| | `discovery` / `claim` | 遺体の発見／死因の偽装の伝聞 |
| 移植 | `chip_removal` / `missing` / `hiding` | チップの摘出／加害者の失踪に気づく／なりすまし |
| その後 | `aftermath` / `now` / `intrusion` | 生存者の記録／現在／侵入と退去（ハッチ記録に対応） |

**手がかり事実の置き方**：[6] で決めた「どの書き手のログに置くか」を保ったまま置く。手がかり事実には書き方の区分 `mode` を持たせる。

| mode | 書き方 | 使える場合 |
|---|---|---|
| `observe` | その場で見聞きしたこととして書く。場面の出来事（`events`）として正本に置く | 正本上、書き手と対象がその時刻にその場所にいる場合だけ |
| `recall` | 前から知っていること（知識・回想・伝聞）として書く。場面の出来事にはしない | 場所を問わない |

観察事実ごとの observe の場面：

| 観察事実 | 場面 |
|---|---|
| `OBS_WORK` | 対象の持ち場での作業（書き手は同僚か、用事で訪れた人） |
| `OBS_MARKER` | 昼食・立ち話・夕食・配給の列（本人の記述なら、自分の作業や朝の会合も） |
| `OBS_NUMBER` | 番号の習慣による：配給カード＝配給の列、私物棚＝夕食、部屋の札＝夜の居住区（書き手が同じ区画の場合だけ） |
| `OBS_AHEAD` | 列＝配給の列、発言順＝朝の会合 |
| `OBS_ADJACENT` | 夕食の席 |
| `OBS_HONORIFIC` | 立ち話・昼食・夕食 |
| `OBS_INGROUP` | 昼食・立ち話・夕食・配給の列・書き手の区画の夜の居住区 |
| `OBS_OUTGROUP` | 昼食・立ち話・夕食・配給の列 |

- 置けない（関係する人物が同じ時間帯に別の場所にいる、など）ときは `recall` として、書き手が居合わせる食事・立ち話・列の場面のエントリに持たせる。
- **1エントリの身元の観察事実は2個まで**（`CFG.scale.idFactsPerEntry`）。候補の場面は、書き手のエントリにまだ余裕のあるものに限る。
- 場面の場所は、正本上のその時刻の書き手の所在から決まる。一人が同じ日に二つの「作業」場面や二つの「夜の居住区」場面に同時にいることはない。
- 候補の場面のうち、書き手がすでに記録している場面を優先し、1場面の記録者は4人まで。
- 背景の出来事には、誰がどこで働いているかなど手がかりになる名前を書かない。持ち場で働く書き手には「自分の作業」の出来事を書き手だけが見聞きするものとして足す。
- 異変前の日常のエントリは1人4件以上（`CFG.scale.dailyEntriesMin`）。足りなければ自分の作業・会合・列・食事などの場面を足し、手がかりを日をまたいで散らす。
- 移植の加害者の場面は、エントリを被害者のログ（`owner`）に、書き手（`writer`）を加害者として記録する。
- 遺体の発見者が見る徴候は、被害者本人が最期に感じた徴候と同じものから選ぶ。

**文化と事件の連動**（改修仕様 v0.2 §6.3）：
- 方針を告げる相談役に偏見があれば、感染症の隔離や内部抗争の夜間外出禁止の対象を、その偏見の向く区画にする（70%）。食料の枯渇で序列が厳格・形式的なら、方針は「配給を古株から順に回す」。理由（偏見・序列観）を会話ログの方針の決定に残す。
- 序列が厳格なシェルターの飢餓では、入居番号の大きい住人から先に死にやすくする（死んだ順番が入居順の手がかりになる。実測で相関 −0.95）。
- 殺人の加害者は、被害者の区画を見下している・対立している区画の住人から選びやすくする（50%）。

主観ログのエントリ種別（`kind`）：

| kind | 内容 |
|---|---|
| `daily` | 異変前の日常の場面の記録。ID の手がかり事実や関係の描写を持つ。1人あたり最低2件 |
| `crisis` | 発端・告知（最大5人）・影響（最大3人）・口論（最大3人）の場面の記録 |
| `final` | 死の直前。`DEATH_SIGN`（外傷は1つ、病気・飢えは1〜2つ、まれに曖昧な「吐き気」）と、必要なら `KILLED_BY` |
| `deleted` | 改ざんで削除されたエントリ（最期と、その数時間前の2件）。本文なし |
| `witness` | 遺体の発見・襲撃の目撃（死後 20〜300 分）。`DEATH_SIGN`、必要なら `KILLED_BY`。誤認トリックの目撃もこの種別 |
| `hearsay` | 死因の偽装の伝聞（`DEATH_CLAIM`） |
| `chipRemoval` | 移植トリックの加害者がチップを摘出する直前（死の描写ではない） |
| `transplanted` | 移植後に被害者のログへ書かれる、加害者の主観 |
| `flavor` | 移植トリックで「遺体が見つからない」と書く住人の記録 |
| `aftermath` / `now` | 生存者の、最後の死の後と現在（`now_day`）の記録。侵入者や食料の状況に触れる |

目撃者は、改ざん対象・最期に加害者を見ていない殺人では必須。それ以外は 50%。
会話ログ（相談役と管理AI）：起動時の定時報告、ID の手がかり（1件ずつ）、異変の協議と方針の決定、物資の報告、死者ごとの「生体信号途絶」（その時刻に行動できる相談役が居る場合）、改ざん・偽装の依頼。危機・死に関わる会話は正本の場面（`scene`）に対応する。相談役が全員いなくなると、管理AIが記録終了を告げる。
外部ハッチ開閉記録：外部偵察（42）の外出と帰還（認証あり）と、侵入者の侵入・退出（認証なし、強制開放）。

### 4.8 人物設定とシェルター文化（`culture.js`。改修仕様 v0.2 §2・§3）

**人物設定**（住人の `profile` に追加）：

| 項目 | 内容 |
|---|---|
| `gender` / `age` / `age_band` | 男性・女性／年齢（相談役以外の 8% は 11〜15 歳の子ども）／子ども・若者・壮年・老年 |
| `pronoun` | 一人称。住人の生成時に選んだものを、性別・年齢に合わせて置き換える（男性の「あたし・うち」、女性の「俺・僕・わし」、50歳未満の「わし」を置き換え。乱数は使わない） |
| `personality_tags` | 性格タグ 2〜3 個（`personality` はその連結） |
| `attitude` | 序列観（重んじる・気にしない・反発する）、区画意識（身内びいき・中立）、偏見（自分以外の区画を見下す・恐れる。なしも） |
| `traits` | 目印ではない持続的な特徴 1〜2 個（LLM が創作した特徴も書き戻す） |
| `markers` | 文化の目印のうち、その住人が持つもの（属性値から自動で付く。描写するかは生成器が決める） |
| `background` | 経歴の一言 |

関係（`relations`）には呼び方 `terms`（`a_to_b` / `b_to_a`）を持たせる。家族は年上の相手を「母さん・父さん・姉さん・兄さん」、師弟は弟子が師を「先生」と呼ぶ。

**シェルター文化**（シナリオ JSON の `culture`）：

| 項目 | 内容 |
|---|---|
| `districts` | 区画ごとの役割（農業・設備・古参・新入り・医療・倉庫から重複なし）、評判、区画外からの呼び名、目印 1〜2 個 |
| `district_relations` | 区画の組ごとの関係（対立・見下し・依存・無関心） |
| `job_markers` | 職能分類の目印（管理班を除く各分類に 40%） |
| `seniority` | 序列の強さ（厳格・形式的・崩れかけ）、番号の習慣（必ず1つ）、順番の習慣（1〜2個）、呼び方（先に来た人へ・後から来た人へ）、序列の帯の目印（60%。入居順 3〜5 以下） |
| `markers` | このシェルターで使う目印の定義（種類・説明・予約語・描写の文） |
| `marker_attr` | 目印 → 属性値（真相。画面には出さない） |

- 区画の割り当ては、役割と職能・入居の早さを確率的に連動させる（役割に合えば重み3倍。必ず一致はさせない）。各区画に最低2人。
- 目印は**決定的**：描写された住人は必ずその属性値を持つ。属性値を持つ住人全員が描写されるわけではない。目印の候補は `config.js` の `culture.markers`。
- 語彙は互いに重ねない：区画の呼び名・序列の呼び方・目印の予約語・「うちの区画」は、どの二つも一方が他方を含まない（例：呼び名に「古株ども」を使うと呼び方「古株の〜」と区別できない）。予約語は、ふつうの言い回しと紛れない語にする（「っちゃ」は「言っちゃった」と、「だで」は「ただでさえ」と紛れるので使わない）。

## 5. 手がかり事実

すべての手がかりは構造化された「手がかり事実」として `facts` に入り、文章はそこから作られる。

```js
{ id: 'f12', type: 'ENTRY_OFFSET', args: { p, q, k }, certainty: 'certain' | 'low' | 'claim',
  mode?: 'observe' | 'recall',   // 主観ログに置く身元の手がかりの書き方（§4.7）
  loc: { doc: 'log' | 'dialogue' | 'hatch', owner?: '<ログの持ち主ID>', index: <エントリ番号> } }
```

主観ログに置く身元の手がかりは、次の**観察事実**だけ（改修仕様 v0.2 §4.2）。文化のルールを学習して初めて身元の制約になる（`OBS_WORK` を除く）。

| 型 | 引数 | 文章での現れ方 | 推理に必要な文化のルール |
|---|---|---|---|
| `OBS_MARKER` | p, marker | 「⟨X⟩の服から湿った土の匂いがした」 | 目印 ⇒ 属性値（区画・職能分類・序列の帯） |
| `OBS_WORK` | p, j | 「⟨X⟩が発電機の配線を点検していた」 | なし（作業内容 ⇒ 職能は常識） |
| `OBS_NUMBER` | p, n | 「⟨X⟩の配給カードには7と刻まれていた」 | 番号の習慣 ⇒ 入居順 |
| `OBS_AHEAD` | p, q, custom | 「配給の列で⟨X⟩の後ろに並んだ」 | 列・発言順 ⇒ 入居の前後（p が先） |
| `OBS_ADJACENT` | p, q, custom | 「食堂では⟨X⟩のすぐ下座が私の席だ」 | 席順 ⇒ 入居の前後 |
| `OBS_HONORIFIC` | p, q, term, custom | 「⟨X⟩先輩」「新入りの⟨Y⟩」（q が話し手） | 呼び方 ⇒ 入居の前後 |
| `OBS_INGROUP` | p, q | 「うちの区画の⟨X⟩」（q が話し手） | 身内の言葉 ⇒ 同じ区画 |
| `OBS_OUTGROUP` | p, nickname, q | 「あの土いじりの⟨X⟩」（q が話し手） | 呼び名 ⇒ 区画 |

次の答えの形の事実は、**主観ログに置かない**（会話ログ＝管理AIの公式な記録にだけ、1シナリオ3件まで）。LLM が文章に書き足した正しい観察は `extra: true` として追加されることがある（§8.2）。

| 種別 | 型 | 引数 | 意味 |
|---|---|---|---|
| 身元 | `DISTRICT` / `NOT_DISTRICT` | p, d | p は区画 d に住む／住まない |
| | `SAME_DISTRICT` | p, q | p と q は同じ区画（「隣の部屋」） |
| | `JOB` / `NOT_JOB` | p, j | p の職能は j である／ない |
| | `JOB_CATEGORY` | p, c | p の職能は分類 c |
| | `SAME_JOB` | p, q | 同じ職能 |
| | `ENTRY_ORDER` | p, n | 入居順は n（1 は「最初」、`max_entry` は「一番最後」と表現） |
| | `ENTRY_OFFSET` | p, q, k | E(p) = E(q) + k（「k人後」。欠番も1人と数える） |
| | `ENTRY_BETWEEN` | p, q, r | q, p, r の順に連続した番号 |
| | `ENTERED_BEFORE` | p, q | E(p) < E(q) |
| 死 | `DEATH_SIGN` | p, sign, causes | 死の直前・遺体の徴候。causes は両立する死因 |
| | `KILLED_BY` | p, k, dark? | p を襲ったのは k（low は誤認の可能性） |
| | `DEATH_CLAIM` | p, cause, claimer | claimer による死因の主張（真偽不明） |
| | `SIGNAL_LOST` | p, t | 管理AIの生体信号途絶の報告 |
| | `LOG_DELETED` | p, by, count | 記録の削除 |
| 他 | `STYLE_SHIFT` | log, writer | ログの途中から別人（writer）が書いている |
| | `HATCH` | t, side, auth | 外部ハッチの開放（`inside`/`outside`、認証者 ID か null） |

**徴候表**（`config.js` の `signs`）：徴候ごとに次を持つ。正本・テンプレート文・LLM 文章化・検証器はすべてここを参照する。

| 項目 | 用途 | 例（銃創 `gunshot`） |
|---|---|---|
| `causes` | 両立する死因（論理層） | `['intruder']` |
| `label` | 抽象的な内容。正本の出来事と、LLM に渡す必須事実に使う | 「チップの応答がない見知らぬ人影に、胸を銃で撃たれた」 |
| `keywords` | LLM 文章化の機械的な事前判定（§8.2） | 銃・撃・破裂音・弾 |
| `template` | テンプレート文章化用の文（`self`：本人の最期、`other`：遺体を見た人。`{V}` は死者） | 「チップの応答がない見知らぬ人影が、銃を構えた。乾いた破裂音。…」 |

徴候と死因の対応：感染症＝発熱・血痰・発疹、被曝＝脱毛・皮膚のただれ・線量計、飢餓＝飢え・衰弱、殺人＝殴打・絞殺・刺傷・突き飛ばし、事故＝転落・感電・瓦礫、侵入者＝見知らぬ人物の刃物・銃創・ガスマスクの人影（どれも「住人ではない者」と読み取れる文にする。銃だけでは住人の犯行と区別できないため）。「吐き気」は感染症・被曝・飢餓のどれとも両立する曖昧な徴候。

## 6. 検証器（`solver.js`）

### 6.1 ソルバー

有限領域・二項制約の CSP。AC-3 で絞り込み、最小領域の変数からバックトラックする。
ID の3要素（区画・入居順・職能）は互いに制約を持たないので、3つの CSP に分けて解く。

- 変数：住人ごと（伏せ字ごと）の値。既知の住人は値を固定。
- 職能：相談役は全員既知（概要に記載）なので、未知の住人の領域から 51 を除く。
- 入居順：1〜`max_entry`、全員異なる（全組に ≠ 制約）。
- 一意性の判定：解を一つ求め、その値を禁止して再度解き、解がなければ一意（設計書 §8.2 の方法）。

### 6.2 到達可能性（§8.2。ルールの学習を含む）

プレイヤーの知識の状態を「既知の ID」と「学習済みの文化のルール」の二つで模擬する（改修仕様 v0.2 §5）。

```
既知ID = 相談役、学習済みルール = 空
ループ:
  読める資料（会話ログ・ハッチ記録・既知者の主観ログ）の身元の事実と観察事実を集める
  既知の人物についての観察（＝例）から、学習できるルールを学習済みに加える
  学習済みルールで観察事実を制約に変換する（例：OBS_MARKER(p, 土の匂い) と「土の匂い ⇒ D区画」から DISTRICT(p, D)）
  CSP で区画・入居順・職能が一意になった人物を既知に加える
  何も増えなければ終了
```

| ルール | 学習できる条件（K＝2） | 変換される制約 |
|---|---|---|
| 目印 m ⇒ 属性値 | m の描写がある既知の人物が K 人以上、反例がなく、**紛らわしくない**（例の全員が共通して持つ属性値が一つだけ。区画・職能分類・序列の帯で判定） | `DISTRICT` / `JOB_CATEGORY` / `ENTRY_MAX` |
| 呼び名 n ⇒ 区画 | 呼び名で呼ばれた既知の人物が K 人以上、紛らわしくない | `DISTRICT` |
| 身内の言葉 ⇒ 同じ区画 | 既知の二人の組が K 組以上、すべて同じ区画 | `SAME_DISTRICT` |
| 番号の習慣 ⇒ 入居順 | 既知の人物の番号が K 人以上、すべて入居順と一致 | `ENTRY_ORDER` |
| 順番の習慣 c ⇒ 入居の前後 | 既知の二人の組が K 組以上、すべて入居順と一致 | `ENTERED_BEFORE` |

`OBS_WORK` は常に `JOB` に変換する。全員に届けば到達可能。各段で解けた ID の列と、各ルールを学習した段を難易度の指標として記録する（`report.reach.rules`）。一意解が真相と食い違えばエラー。

### 6.3 一意性（§8.3）

全資料を読める前提で、次を手がかり事実から導き、真相と一致するか確かめる。

- 生死：確かな `DEATH_SIGN` があれば死亡。ログの最終更新が `now_day` に達していれば生存。ただし `STYLE_SHIFT` のあるログは書き手側の生存の証拠として扱う。両方・どちらもなしは不定（エラー）。
- 死因：その人物の確かな `DEATH_SIGN` の causes の共通部分が1つに定まること。
- 加害者：確かな `KILLED_BY` が1人だけを指すこと（low と claim は使わない）。
- 侵入者：認証なしのハッチ開放のうち最後が「外側から」なら、中に居る。
- 安全判定：上から §4.5 の規則で導き、真相と一致すること。

### 6.4 構造検査

生成時に必ず実行し、違反があればシナリオ生成の失敗として生成器の再試行に回す（LLM には渡さない）。

- **文章**：各エントリについて、割り当てた手がかり事実がすべて文章化されていること（`rendered`）、事実の対象人物のトークンが本文にあること、書き手本人のトークンが本文に無いこと、事実の所在とエントリが対応していること。
- **物語の正本と場面カード**（`verifyCanon`）：
  - 場面カードの場所＝正本上のその時刻の書き手の所在（書き手がその場面の `participants` にいる）。エントリは場面より後の時刻に書かれる。
  - 一人が同じ日に二つの「作業」場面や二つの「夜の居住区」場面にいない。死亡後の人物が場面にいない。
  - 書き手に渡す出来事（`perceived`）は、書き手が見聞きした出来事だけ。
  - `observe` の手がかりは、対象の人物がその場面にいて、書き手が見聞きした出来事として正本にある。
  - エントリごとの違反（`byEntry`）は、LLM 文章化の前の検査（§8.2）でも使う。
- **手がかりの形**（`verifyClueForm`。改修仕様 v0.2 §11 第1段階）：主観ログに答えの形の事実（`DISTRICT` などの直接の事実）がない。1エントリの身元の観察事実が2個以下。異変前の日常のエントリが1人4件以上。会話ログの直接の事実が3件以下。学習される文化のルールが2個以上。
- **死因の不変条件**（`verifyCauseInvariants`）：
  - すべての `DEATH_SIGN(p, sign, causes)` の `causes` が p の真の死因を含む。
  - `deaths[].signs` の各徴候が、徴候表で `deaths[].cause` と両立する。
  - `intruder` の死に住人の加害者が付いていない。`murder` の加害者は住人。それ以外の死因に加害者が付いていない。

## 7. 文章化（テンプレート、`narrator.js`）

- 人物は本文中で `{P:ID}` と書く。書き手本人は `{I}` と書き、最後に一人称へ置き換える。
- 事実の型ごとに複数の文型があり、乱数で選ぶ。職能は職能名ではなく作業内容で表す（例：電気＝「発電機の配線を点検していた」）。作業の描写は `Narrator.JOB_TASKS` の1種類に固定し、正本・テンプレート文・LLM の検証で共通に使う。
- 各エントリは場面への入り方（持ち場の作業／訪問／朝の会合／配給の列／食事／立ち話／居住区／告知／口論など）から始まる。
- 観察事実の文は、文化の語彙（目印の描写の文、番号の習慣、呼び方、区画の呼び名）を使って書く。答え（区画・入居順・職能を直接述べる文）、文化のルールの一般論、否定は書かない。`recall` のときは「いつも〜」「たしか〜」のような知識・回想の文にする。
- 同じエントリで、人物以外が同じ文になった場合は文型を選び直す。
- 語り口：一人称、口癖（エントリの締めに 70%。移植関連のエントリでは必ず入れる）、文末の癖。
- 会話ログは `{speaker, text}` の行の列。話者は相談役の ID か `AI`。

## 8. LLM による文章化（`llm.js`）

### 8.1 設定（`js/config.local.js`、git 管理外）

```js
window.ASARIYA_LOCAL = { openai: {
  apiKey: 'sk-...',          // 必須（「ここに」を含むひな形の値は未設定扱い）
  model: 'gpt-5-mini',       // 生成モデル（既定）
  verifyModel: undefined,    // 抽出（往復検証）モデル。省略時は model
  reasoningEffort: 'low',    // 推論モデル用。非推論モデルでは指定しない
  baseUrl: 'https://api.openai.com/v1',
  concurrency: 4,            // 同時に処理するログ数
  maxRounds: 3,              // 1回の実行での再生成回数
  timeoutSec: 120,           // 1リクエストの制限時間
  autoNarrate: true,         // シナリオを開いたら自動で文章化
  testIncludeDraft: false,   // テスト専用。true のときだけ下書きを _draft として添える（API のスタブ用）
} };
```

API はブラウザから直接呼ぶ（Chat Completions、`response_format: json_schema, strict`）。OpenAI は `file://`（Origin: null）からの CORS を許可している。キーはブラウザから送られるため、公開サーバーに置かない前提。

### 8.2 処理の流れ

対象は主観ログの削除されていないエントリ。生成の単位は**場面**で、物語の正本（§4.7）に沿って時系列順に進める。

0. **事前検査**：場面カード自体が正本と矛盾しているエントリ（§6.4 `verifyCanon` の `byEntry`）は、LLM を呼ばずに仕様エラー（`canon_invalid`）とする。
1. **時刻帯に分ける**：エントリを時刻順に並べ、1日ずつの「時刻帯」に区切る（エントリが6件未満の日は次の日とまとめる。`BAND_MIN`）。時刻帯は順番に処理し、時刻帯の中は並列に処理する。
2. **呼び出しに詰める**：時刻帯の中の未処理エントリを場面ごとにまとめ、場面を分けずに1回の呼び出しへ8件程度ずつ詰める（言い直しは2件程度ずつ）。同じ場面を記録する書き手全員を1回で書かせるので、事実は揃い、視点は書き分けられる。`concurrency` 呼び出しずつ並列。
3. **別名化**：呼び出しごとに、人物トークンを `<P1>`, `<P2>`… に置き換える（ID から区画などが漏れないように）。書き手自身は出来事の文中で「書き手」と書き換え、別名は `writer_alias` として渡す。
4. **生成**：
   - 場面カードごとに渡すもの：時刻・場所・題・暗闇か、背景（原因の場面）、それまでに確定した細部（同じ場所・同じ人物・原因の場面のもの、最大10件）。
   - エントリごとに渡すもの：書き手の語り口、場面の説明、感情、書き手が見聞きした出来事（`perceived_events`）、書き手が気づいた人物（`people_noticed`）、必ず含める内容（`must_include`）、口癖を入れるか（`use_tic`）、注意、前回の指摘。
   - **テンプレートの下書きは渡さない**（文言の写しを防ぐため。下書きはキャッシュのキーと、テンプレート文で確定する場合のためだけに持つ）。
   - `must_include` は完成した文ではなく抽象的な内容で渡す。徴候は徴候表の `label`、身元の手がかりは書き方の区分つきの内容（例：「⟨P2⟩ が B区画の住人であること（前から知っていることとして、回想・伝聞・知識の形で伝える。この場面の出来事にしない）」）。
   - 指示：
     - 場面カードにない出来事・人物・物を新たに登場させない。住人どうしの関係や素性（同じ区画・隣人・同じ持ち場・家族など）も、必須の内容や見聞きした出来事にないものは書かない。足してよいのは感覚・感情・内面の描写だけ。
     - 書き手の語り口には、書き手自身の住む区画も渡す（「私たちの区画」と誤って書かないように）。
     - 台詞はカードの出来事（告知・口論など）の中身としてだけ言わせる。仕事の場面ではカードの作業そのものを描く。
     - 事実を説明文として書かない。行動・会話・感覚の中で間接的に伝える。悪い例「⟨P2⟩はB区画に住んでいる。」、良い例「帰りがけ、B区画の通路で⟨P2⟩が自室の鍵を探していた。」（observe）／「⟨P2⟩とはB区画の配給列でよく一緒になる。」（recall）。
   - 出力は `{entries:[{key, text}]}`。
5. **機械的な検査**：本文の長さ、ID の書き込み、必須の事実に出てくる人物の欠落、書き手が気づいていない人物の登場、書き手本人の記号、口癖の有無。移植トリックに関わるログでは一人称の有無も検査する。機械的な検査に通ったものだけを往復検証にかける。
   「書き手が気づいた人物」（`people_noticed`）は、どの場面でも**書き手が見聞きした出来事に出てくる人物だけ**とする。場面の参加者全員を渡すと、書き手が知覚していない人物（最期に見ていない加害者など）や、手がかりになる名前まで書かれてしまうため。
6. **往復検証**：別の呼び出しで、本文から3種類を抽出させる。場面の説明・死因の判断基準・職能ごとの典型的な作業を与える。
   - **手がかり事実**の照合：
     - 書き漏らし：必須の事実がすべて読み取れること（「吐き気」は単独では判定しない。`ENTRY_BETWEEN` は、3組の順番関係のうち2つが `ENTRY_OFFSET` として読み取れれば可）。入居順の差は、抽出では「p＝後に来た人、q＝先に来た人、value＝正の人数」で表させ、LLM にも「〜の方が n 人先」と向きのはっきりした内容で渡す。必須の `DEATH_SIGN` は、徴候表の `keywords` のどれかが本文にあれば、抽出結果を待たずに書き漏らしなしとする（機械的な事前判定）。
     - 書きすぎ：必須でない事実が真相と矛盾しないこと。身元の事実は真相と照合し、`DEATH_SIGN` は死者・正しい死因（または unknown）に限る。`DEATH_CLAIM` は指定されたものだけ許す。
       侵入者による死で、本文に侵入者の徴候のキーワード（見知らぬ・チップの応答・ガスマスク・銃など）があるのに抽出が `murder` と答えた場合は、食い違いとしない（読み手には住人でない者だと伝わっているため。抽出役にも「住人でない手がかりが一つでもあれば intruder」と指示している）。
     - 加害者の記述（`KILLED_BY`）：特定の住人の人物記号を加害者として名指ししたら、指定された `KILLED_BY` と一致しなければ不合格。正体不明の襲撃者（抽出で `q="unknown"`。顔の見えない人影・見知らぬ人物）は、その人物の真の死因が `murder` か `intruder` なら許し、それ以外（病気・飢え・事故）なら不合格。抽出役には「人物記号を推測で当てはめない」と指示する。
   - **出来事**の照合：本文が「実際に起きた」と主張する出来事（いつ・どこで・誰が・何を）を、場面カードのどの出来事に当たるかと一緒に抽出させる。カードにない出来事（presence 以外）、書き手が見聞きしていない出来事、その場にいない人物が加わる出来事は不合格。前から知っていること・以前の思い出し（recall）は出来事に含めない。書き手自身の身振り・姿勢・表情・声の調子・ため息・独り言・口癖、感覚（聞こえた・見えた）、待つ・見守るといった反応も出来事に含めない（足してよい「感覚・感情・内面」の範囲）。
   - **細部**（台詞・物の状態・場所の様子）は、合格したら書き戻しに使う。
7. **日ごとの整合性検査**：その回に合格した候補がある日ごとに、正本のその日の場面と、その日の全ログ（確定済み＋今回の候補、各エントリの場面の説明つき）を並べて、矛盾を LLM に指摘させる。
   - 矛盾ごとに、関わるエントリ（`keys`）と、直すべきエントリ（`culprits`：正本や他の多数の記録から外れている側）を挙げさせ、`culprits` に当たる今回の候補だけを差し戻す（同じ場面の全員を巻き添えにしない。確定済みの記録は直さない）。
   - 記録が書かれた時刻と出来事の時刻のずれ、死ぬ瞬間の記録、推量の食い違いは矛盾としない。
   - 住人の区画・職能・入居順についての記述は判定に使わない（往復検証で真相と照合済み。検査役が「医務室で働く」と「看護ではない」を矛盾と誤判定したため）。検査役が指示に反して挙げることがあるので、指摘の内容が職能・所属・区画・入居に関するものは機械的に除外する。
   - 誰かの主張や公式の記録（偽装・改ざんの死因など）と、実際の様子の食い違いは矛盾としない（主張は偽りでありうる）。
   - 正本としては、その日の場面に加えて、並べる記録が属する場面も渡す（前日の死を日付をまたいで書いた記録を、同じ場所の別の死と取り違えないように）。
8. **確定と書き戻し**：差し戻されなかった候補を確定する。時刻帯が終わるたびに、確定した文章の細部を場面の `details` に書き戻す（1場面10件まで）。後の時刻帯の場面カードに「確定した細部」として渡る。
9. 不合格のエントリは指摘を添えて再生成する（時刻帯ごとに最大 `maxRounds` 回）。指摘は `{P:ID}` で持ち、呼び出しごとの別名に変換して渡す。

**v0.2 での入力と検証**（改修仕様 v0.2 §7・§8）：
- 生成の入力に加えるもの：シェルターの文化（区画の性格・評判・呼び名、区画どうしの関係、序列の強さ・習慣・呼び方）、目印の**予約語**（描写の説明と語。どの属性の目印かは渡さない）、書き手の人物設定（性別・年齢・性格・語り口・文化への態度・人間関係と呼び方・持続的な特徴・経歴・住む区画）、登場人物の設定（書き手が知る範囲：性別・年齢層・書き手との関係と呼び方・持続的な特徴）。
- 守る情報（区画・入居順・職能に関わる描写、目印、序列の習慣の観察、身内・余所者の言葉づかい、性別・年齢、関係と呼び方、誰がいつどこにいたか、死の徴候、加害者）は設定と場面カードのとおりに書かせ、指定のないものは書かせない。自由な情報（感情・内面・思い出、物の見方、文化への態度、偏見の内容、天気や食事など）は自由に盛らせ、照合しない。
- 抽出役には守る情報だけを抽出させる。観察事実（`OBS_*`）、直接の答え（`DIRECT`）、関係（`RELATION`）、性別（`GENDER`）、死の事実、文化のルールの一般論（`general_rules`）、人物が関わる出来事、細部。
- 判定：
  - 必須の事実が読み取れない → `missing_fact`（目印は、予約語と対象の人物が同じ文にあれば読み取れたとみなす）
  - 予約語が指定外の人物・文脈に使われている → `reserved_marker_misuse`（機械的な検査と抽出の両方）
  - 文化のルールの一般論 → `rule_stated`。区画・入居順・職能の直接の記述 → `direct_answer`。性別の取り違え → `gender_mismatch`。設定にない関係・真相と矛盾する観察 → `false_fact`
  - 指定にない**正しい**観察 → 確定のときに手がかり事実に足して推理の模擬をやり直し、予定より早く特定できる人物が出る、または1エントリ2個を超えるなら `stage_order_broken`。崩れなければ `extra: true` の事実として正式に追加する
  - 人物が関わらない出来事は自由な情報として照合しない
- 創作した他人の持続的な特徴は `new_traits`（エントリの key・人物・特徴）として出力させ、確定のときに人物設定に書き戻す（以降の生成に渡る）。予約語と重なれば `trait_collision`。
- 生成は時系列順に、1日ずつの時刻帯で行う（エントリが6件未満の日は次の日とまとめる。同じ時刻帯の中は並列）。
- 誤検出を避けるための例外：
  - 場面カードで告げられた方針（「配給を古株から順に回す」「〜区画を隔離する」など）を言い直した記述は、答えにも文化のルールの一般論にも数えない（方針の出来事に、言い直しに出やすい語を持たせて照合する）。
  - 相談役であること・相談役の素性は答えに数えない（最初から分かっている）。
  - 答え（`DIRECT`）かどうかは抽出係の要約ではなく本文で判定する。本文に職名・職能分類・「〜区画」「〜番目に」「入居」などの答えの語がなければ、観察の言い直し（「〜する仕事をしている」「カードの番号は17だった」）とみなす。
  - 作業の観察（`OBS_WORK`）は、対象の人物と同じ文に、その職能の典型的な作業の描写がほぼそのまま（2文字単位で半分以上一致）あれば読み取れたとみなす。推量の目撃（誤認）は、加害者の記号と推量の言い回し（たぶん・気がする など）が同じ文にあれば読み取れたとみなす。
  - 抽出された死因が真相と違っても、本文にその死因の徴候の語が一つもなければ抽出の読み違いとみなす（例：被曝の皮膚のただれを感染症と読む）。
  - 指定外の正しい手がかり（extra）は、対象の人物の記号が本文にある場合だけ追加する（呼び方だけで書かれた人物を抽出係が当てはめたものは使わない）。
  - 日ごとの整合性検査では、誤認として書かせた推量、回想として書かせた作業の描写、管理AIの「生体信号の途絶」と本人の記録の食い違い（チップの摘出）は、矛盾として扱わない。
  - 予約語の機械的な検査は、書き手以外の人物の記号がある文だけを見る。記号のない文（書き手自身や情景の描写）は、抽出で誰の目印として読めるかを判定する。
- 人物は呼び方（「父さん」）や区画の呼び名（「土いじり」）だけで指させず、記号を必ず添えさせる（「父さんの<P1>」「あの土いじりの<P4>」）。
- 予約語を含む細部は正本に書き戻さない（後の場面で指定外の人物に目印が書かれるのを防ぐ）。
- 列・席・発言の前後、番号、呼び方は、指定されたもの以外を書かせない。会合の発言順は二人の前後だけを書かせ、「最初に」「まず」のような全体での順番は書かせない（記録者ごとに別の組を書くため、食い違う）。
- 言い直し（2回目以降の生成）は、1回の呼び出しに2件程度ずつ入れる（1回目は8件程度）。まとめて生成したときの書き落としを言い直しで繰り返さないため。

**指摘の種類のコード**：指摘はすべて `{code, msg}` で持つ（LLM には `msg` だけを渡す）。

| 区分 | コード |
|---|---|
| 機械的な検査 | `length` / `id_leak` / `unknown_person` / `missing_person` / `absent_person` / `self_token` / `tic` / `pronoun` |
| 手がかり事実の照合 | `missing_fact` / `false_fact` / `cause_mismatch` / `unauthorized_killer` / `unauthorized_claim` |
| 正本との照合 | `scene_conflict`（場面カードにない出来事・同じ日の他の記録との矛盾） / `canon_invalid`（場面カード自体が正本と矛盾。事前検査で検出） |
| 文化・人物（v0.2） | `reserved_marker_misuse` / `rule_stated` / `direct_answer` / `gender_mismatch` / `stage_order_broken` / `trait_collision` |
| 一時的なもの（仕様エラーの判定に数えない） | `no_output` / `no_extraction`（応答が得られなかった） |

**仕様エラー**：同じエントリで、同じ種類の指摘が2回続いたら再生成を止め、`report.specErrors` に記録する（`canon_invalid` は即座に）。記録する内容は、エントリ・場面カード・必須の内容・指摘・最後の出力。仕様エラーのエントリはテンプレート文で確定する（プレイヤーへの選択は出さない）。再生成で直らない原因（下書き・正本・検証器の側の不具合）を、文章の問題（`unresolved`）と分けて見えるようにするため。

**下書きとの重複率**：LLM の文章とテンプレートの下書きの、文字 5-gram の一致率（出力の 5-gram のうち下書きにも現れる割合。人物トークンは同一視）。`report.overlap` に LLM の文章全体の平均を出し、検証器パネルと `batch-check` に表示する。

### 8.3 失敗時の扱い

- **仕様エラー**：§8.2 の仕様エラーは自動でテンプレート文に確定し、端末ログに件数を出す。内訳は検証器パネルに一覧する。
- **検証に通らない**：仕様エラー以外で `maxRounds` 回で通らなかったエントリは、未処理のまま `report.unresolved` に入る。画面はエラーを表示し、プレイヤーが選ぶ。
  - 「さらに再検証する」：前回の指摘を引き継いで、もう一度最大 `maxRounds` 回。
  - 「テンプレート文を使う」：そのエントリをテンプレート文で確定（`useTemplate`）。以後 API に送らない。
  - 失敗の詳細（指摘と最後の出力）は「ネタバレを含む」として折りたたんで表示する。
- **通信エラー**：タイムアウトと通信失敗は最大3回まで再送（1秒×2^n 待ち）。429・5xx は `retry-after` に従い最大4回まで再送。401・404 などは即座に致命的エラー。致命的エラーでは「再試行する」か「テンプレート文で遊ぶ」かを選ぶ（後者は未処理のまま残り、上部の「LLMで文章化」から再開できる）。
- **中断**：進捗ダイアログの「中断してテンプレート文で遊ぶ」または Esc。合格した分は保存済み。

### 8.4 キャッシュと状態

- エントリの `narrator`：未設定＝未処理、`'llm'`＝LLM の文章、`'template'`＝テンプレート文で確定。元のテンプレート文は `draft` に残す。
- localStorage `asariya:llm:v4:<seed>:<model>` に保存する（プロンプトを変えたら版を上げる）。合格した文章に書かれた指定外の正しい手がかり（`extras`）と、創作した持続的な特徴（`traits`）も保存し、開き直したときに戻す。
  - `entries`：`"<owner>#<index>"` ごとに `{draft, text}`（合格）または `{draft, failed:true}`（テンプレート確定）。
  - `details`：場面ごとの書き戻した細部。
  - シナリオを開くと、下書きが一致するものだけ自動で当て、細部も正本に戻す（API は呼ばない）。
- 検証器パネルから「未処理分を文章化」「キャッシュを消して作り直す」「テンプレート文に戻す」ができる。

## 10. プレイ用 UI（`game.js`）

### 10.1 画面

- 上部：シェルター名・現在時刻・シード、文章の状態（テンプレート／LLM n/m）、警戒度、ボタン（LLMで文章化・最終回答・新しいシナリオ・検証器）。
- 左：資料の一覧。資料は「漁り屋の手引き」「シェルター概要」「職能コード表」「外部ハッチ開閉記録」「相談役と管理AIの会話ログ」。その下に解読済みの主観ログ（ID と最終更新。最終更新が現在日なら緑）。
- 中央：資料の本文。伏せ字は `⟨x9Kq⟩`、解読済みは名前で表示。主観ログは日時・感情ラベル・本文。削除済みエントリは帯で表示。
- 右：ID 認証（入力欄と結果ログ）と人物索引（閲覧中の資料に出てくる人物、選択した人物のメモと出現箇所）。

### 10.2 ID 認証と警戒度

- 入力は全角・小文字・区切りの揺れを吸収する（例 `c-7-31` → `C-07-31`）。
- 形式外、または存在しない区画・入居番号・職能コードを含む ID は送信せず、警戒度は上がらない。
- 正しい ID：その主観ログが開き、全資料の伏せ字が一斉に名前に置き換わる（強調表示）。
- 誤った ID：警戒度＋1。同じ誤りの再入力では上がらない。上限（`CFG.alertMax`＝8）に達すると接続が遮断され、真相が開示される。
- 正しい ID：警戒度を1下げる（0 未満にはならない。`CFG.alertRecoverOnSuccess`）。文化のルールが「なんとなく」の段階で ID を試して仮説を確かめられるようにするため（改修仕様 v0.2 §9）。
- 「漁り屋の手引き」には、答えの読み方（隣の部屋＝同じ区画など）は書かず、「暮らしぶりの中に手がかりがあり、決まりごとはシェルターごとに違う」とだけ書く。

### 10.3 最終回答

- 全住人について、状態（生存／死亡）、死因、加害者（殺人のとき）を選ぶ。加えて安全判定（安全／危険＋理由の複数選択／価値なし）を選ぶ。
- 提出は1回きり。採点：
  - 住人ごとに、身元（ID を解読したか）・生死・死因・加害者がすべて正しければ正解。
  - 安全判定は結果と理由の集合が一致すれば正解。
  - すべて正しければ「完全解明」。
- 結果画面：得点、トリックの解説、住人ごとの真相（記録上の死因との違いを含む）と回答の照合。「同じシナリオをやり直す」「新しいシナリオ」ができる。

### 10.4 保存

localStorage `asariya:v1:<gen|json>:<seed>` に、解読順・警戒度・拒否済み ID・メモ・回答・結果・端末ログを保存する。

### 10.5 検証器パネル（開発用）

- シード指定の生成、ランダムなシード、JSON の出力と読み込み。読み込み時に検証し、失敗しても確認のうえ読める。
- 現在のシナリオの検証レポート（段数・各段の人数・エラー）と真相（折りたたみ）。
- LLM 文章化の状況と操作（§8.4）：合格・未解決・仕様エラーの件数、下書きとの重複率、API の呼び出し回数とトークン。仕様エラーは「未解決」とは別に、エントリ・コード・場面カード・必須の内容・指摘・最後の出力を一覧する。
- 一括検証：開始シードと本数（最大500）を指定して生成・検証し、表にする。

```
node tools/batch-check.js 1 20          # シード 1〜20 を生成・検証（テンプレート文）
```

## 12. 既知の課題・未実装

- **仕様エラーが 0 になっていない**：シード 1〜20 の最終確認で 5 件（§8.5）。仕様側の原因は見つけたものを直し、残りは LLM の書き落とし（人物の記号・番号）。仕様エラーの定義（同じ種類の指摘が2回続けば仕様エラー）では、LLM の書き落としが続いた場合も数える。
- **一人称の揺れ**：LLM が同じエントリの中で一人称を言い換えることがある（「自分」と「俺」）。一人称の検査は移植トリックに関わるログだけ。性別と一人称の組み合わせは生成時に揃えている（§4.8）。
- **性格の読み取りやすさ**：短い日常のエントリでは性格が薄い。口癖が文頭と文末で繰り返される。
- **文化のルールの学習の模擬は単純化している**：例が2つ（K＝2）あれば学習できるとみなす。実際のプレイヤーに必要な例の数、仮説の立てやすさは未検証。
- **席の隣接は前後関係としてだけ使う**（`OBS_ADJACENT` を二項制約にしない。§3）。
- **予約語の判定**：他人の記号がない文の予約語（情景の描写など）は、抽出係の判定に任せている。方針の言い直しの除外は、方針ごとの語の一覧（`story.js`）に頼っている。
- **LLM 文章化の所要時間**：時刻帯（1日）ごとに順に生成し、言い直しを小さな単位で呼ぶため、1シナリオ約 6〜7 分。時刻帯の最小件数（`BAND_MIN`）・1呼び出しの件数（`CALL_SIZE` / `RETRY_CALL_SIZE`）・`concurrency` で調整できる。
- **正本の細部の書き戻し**は、同じ時刻帯の中の他の場面には届かない（並列に生成するため）。時刻帯をまたぐと届く。
- **日ごとの整合性検査は LLM の判断**に頼っている。誤った指摘で差し戻されることがある（時刻のずれ・主張と真相の食い違い・身元の記述は誤指摘しないよう指示し、身元に関する指摘は機械的に除外している）。
- **難易度は未調整**：指標の記録のみ（設計書どおり）。移植トリックの摘出場面のように、露骨な描写がある。
- **テンプレート文の繰り返し**：LLM を使わない場合、言い回しの重複が目立つ。
- **会話ログは LLM の対象外**。
- **トリック4の「記録から消された住人」は未実装**。入居番号の欠番は推理に使われていない。
- **管理AIが把握している関係**は資料化していない（設計書 §14 のデフォルトどおり）。
- **シナリオ JSON に真相が含まれる**ため、そのまま配布すると答えが分かる。
- 作業フォルダの git リポジトリのルートが `C:\`（ドライブ直下）になっている。`.gitignore` は `asariya/` 直下に置いてあり、どちらの構成でも有効。
