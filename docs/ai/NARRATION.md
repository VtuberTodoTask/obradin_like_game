# v2.1 主観ログ全文の生成・意味検証

更新日：2026-10-07。今回更新された [FIXES.md](FIXES.md) への対応。以下の本文・JSONは開発用で、正解と人物対応を含む。

## 原因を確認できた範囲

旧v2には、自由な補筆を生成させながら必須観察の完全コピーを要求する検査があった。`observation_changed / atmosphere_invalid / atmosphere_rejected` を本番v2.1から除去した。ユーザーが報告した30件の実出力は手元に保存されておらず、それらを30件の論理矛盾やAIの意味変更と断定していない。ブラウザの30件復帰は表示と復元の再現用スタブである。

新方式の実API出力を保存して、次の問題を再現・修正した。

| 分類 | 再現した問題 | 対応 |
|---|---|---|
| 入力・変換 | 時刻4910等を日時へ変換せず渡す。一人称がどの人物か不明。修正の期待値に内部IDが残る | 日時へ変換し、書き手参照を明示。別名・SELFを内部人物へ復元。修正指摘にも同じ変換を適用 |
| 検証の契約 | 文書の内容を閲覧した記録までreportedに分類。鍵の受領を否定の出来事として渡す | 情報源と主張の種類を定義。受領は肯定、複製・貸与なしは個別の否定制約 |
| 決定的な比較 | 「BがAの直前」をNEXT(A,B)と抽出したらPREVIOUS(B,A)と一致しない | 隣接関係の二つの向きを厳密に同じ形へ変換。単なる前後関係は隣接へ昇格しない |
| 許可範囲 | 「記録を心に留めたい」を無許可の出来事に分類 | 推理条件を増やさない本人の意向を許可。保存本文の再監査でallowedを確認 |
| 必須証拠の不足 | 専任資格の具体的な職種が生成入力にない。WORKの当番と実作業、ACKの警告読解が曖昧 | 資格の職種を構造化。実作業、警告の署名・復唱・解除の選択も契約に保持 |
| 本文・読解 | 「直前」を「先」だけにする、鍵が割り当てられていないと書く、接触の読み取りが揺れる | 保存した本文・抽出・引用・期待値で確認。不合格のまま復帰し、検査を外して採用しない |

鍵の所持資料では「専任資格」だけを示し、職種は匿名の操作履歴に示す。鍵の人物へ職種を先に教える変更は採用していない。未知人物の正体や移植後の書き手は生成入力へ追加しない。

## 本番の工程

1. プログラムが正本と型別の意味契約を保持する。人物・主体/対象・時刻/区間・値/単位・情報源・主張の種類・否定・知覚範囲を分離する。
2. 必須証拠の意味、人物設定、公開規定、直前の記録、確定した同場面資料を渡して全文を生成する。完成文のコピーは要求しない。
3. 独立した抽出器が本文・全証拠語彙・参照・ヘッダーから観察と引用を返す。この段階には期待する証拠一覧を渡さない。
4. 別の呼び出しで引用と抽出の対応、自然な同義表現、追加・視点を監査する。期待値との比較はこの後段で行う。
5. プログラムで人物・重要値・時刻・否定・情報源・主張の種類を比較する。引用の実在、人物・数値による支えも確認する。自由文字列の言い換えは監査と実在する引用が必要。
6. 問題のあるエントリだけ、具体的なフィールド・期待値・実値・引用を添えて既定2回まで修正する。各修正も同じ検査を通す。
7. 不合格なら同じ証拠の検証済みテンプレートへ戻す。反復だけを「仕様エラー」とは呼ばない。

テンプレート本文は限定文法で読み戻す。採用した自由文は、独立抽出・引用・監査の記録を本文ハッシュ、契約ハッシュ、証拠版、プロンプト版へ結び付けて読む。本文を「眠い。」へ変えれば、内部事実IDが残っていても掲載検査はFAILになる。

自己の最期の感覚はLAST_SENSE、脈拍信号停止は医療端末のPULSE_ENDとして自動付記に分離した。入居受付票の用途、欠番のない台帳、職場の当番規定は概要の世界内資料で読める。「配給券ではない」「手伝いではない」「医師への呼びかけではない」等を各主観ログへ繰り返さない。測定票にはmSvとゲーム内医療基準、架空病Kの判定コードを示す。

## 本文・構造・抽出の具体例

全文と構造化データは [narration-examples.json](narration-examples.json) に5件保存した。うち4件は実APIの保存済み抽出・監査、1件は数値を変えた対照サンプル。回帰テストの再照合でAPIは呼ばない。

### 1. 自然な入居番号の表現：採用

テンプレートは「入居受付票を確かめた。人物の入居順の欄は3番だった」。実際の全文は次のようになった。

> 入居台帳には、\<P1\>が受付順で3番と記されていた。

契約は `NUMBER {p: C-03-31, n: 3}, source_kind=document, modality=observed`。本文から同じ人物と3番をNUMBERとして抽出し、引用を監査して採用した。元文との完全一致や字数で拒否しない。漢数字「三」の採用は別の照合テストで確認した。

### 2. 同じ隣接関係を逆の向きから表現：修正後は採用

> 入居台帳の受付順を見た。そこには、\<P2\>の入居が\<P1\>の直前に記録されていた。

契約は `PREVIOUS {p: C-03-31 (<P2>), q: A-04-23 (<P1>)}`。実抽出は `NEXT {p: <P1>, q: <P2>}`。引用の監査はsupported=trueで、両方とも同じ隣接関係だった。初期実装では型だけで拒否していた。現在は向きをそろえて採用する。人物を入れ替えずにNEXTへ変える、または「先に入居した」だけにする対照例は拒否する。

### 3. 操作鍵350を305へ変える：拒否

対照例の本文は「番号305の操作鍵を受け取った」。他の人物・期間・資格・否定は保持した。

契約は `KEY {serial: "350", ...}`、抽出は `KEY {serial: "305", ...}`。`changed_value`, `field=serial`, `expected=350`, `actual=305` と該当引用を返して不採用。さらに本文が305なのに抽出器が350を返す対照例も、引用の数値検査で拒否する。これは照合のテストであり、実AIが350を305にした測定ではない。

### 4. 具体的な資格と機械記録：採用

> 私は端末の自動履歴で、D04 10:00に隔離盤白のシリアル707が遮断を解除して通電したことを確かめた。これは電気の専任資格を持つ者による操作で、ほかの操作はなかった。仲間を救うため、どうか守りをお与えください。

契約は `SWITCH {t: D04 10:00, device: 隔離盤白, serial: 707, operation: 遮断を解除し通電, qualification: 電気の専任資格}`、情報源machine、資格照合と他の操作なし。本文の実抽出と引用監査が一致し、祈りは本人の既存設定・感情として許可した。「資格を満たした」だけの保存本文は、職種を確定できず拒否する。

### 5. 鍵の所持文書と本人の祈り：採用

> 私は鍵の貸出票を確認した。専任資格の欄で\<P1\>の資格を照合できた。鍵707はD04 09:45から10:21まで\<P1\>に割り当てられ、重複も移管もない。仲間を救うための権限が、どうか正しく使われますように。

契約はKEYの人物、鍵707、所持区間、専任資格、複製・貸与なし、文書の内容。本文からそれらを抽出して採用した。人物の職種・殺意・新たな接触やアリバイを付け足さず、本人の祈りを残している。複製と「重複」の読解など、自由文にはLLM判定の限界が残る。

実際に新規生成した全文は**23件**。生成23回＋修正26回、抽出70回、監査70回、計189 API呼び出し。総トークン455340入力 / 104227出力。金額は利用明細を取得しておらず未算出。対象選択はNUMBER / WORK / PREVIOUS / KEY / ACK / PLAN / LAST_SENSE / TEST / ALIBI / SWITCHで、成功例だけを母数にしていない。

修正後10件の初回・最終率は60%・70%だが、さらに証拠契約・比較を修正した開発過程の測定であり、現行版の全シナリオ成功率ではない。最終の10件再検査では接触の抽出欠落、操作資格の職種不足、鍵の資格・本人意向の判定を拒否した。後者の意向判定は修正済み。接触の読解・同義判定には未解決の揺れがあり、指示書§12に従って固定1本＋ランダム3本の全エントリの大量API生成には進んでいない。

「真の意味変更」「誤検知」の**人による確定値は未測定（null）**。自動分類、実装で再現した誤拒否、未確定の読解を区別する。初期10件では検証不確実の指摘を含むエントリが8、修正後10件では2。最終再検査で未解消のverification_uncertainは0でも、抽出欠落等の分類が正しいことまで人が保証した数字ではない。品質警告は初期1件、修正後0件で、人による自然さの評価ではない。

初期診断はユーザー入力・出力・抽出・監査・参照対応を保存している。システムプロンプト自体を保存する機能は最後に追加したため、これらの過去の実API記録にそのフィールドはない。以後の生成・再検査ではシステム文も保存する。APIキー・認証ヘッダーは保存していない。

## 診断・キャッシュ・残る確認

現行形式2.1、キャッシュ6、証拠版semantic-3、プロンプト版whole-log-4。本文と契約だけでなく、公開規定・人物設定・参照した以前の本文・モデル・検証版で再利用を判断する。再検査には元の別名対応を使い、変更された記録に依存する後続は再処理対象へ戻す。

開発パネルには生成入力、全文、抽出、引用、期待値/実値、参照対応、修正履歴と由来を表示する。エントリ単位の初回/最終採用・復帰と、呼び出し単位の回数・トークンを分ける。過去に出た指摘の集計と、最後に残った指摘も別に保存する。「表示中のシナリオPASS」はテンプレート復帰後を含む現在の本文の検査で、LLM全文が全部合格したという意味ではない。

一般的な日本語の意味・自然さは完全な数学的保証ではない。曖昧な引用やLLMの誤抽出・誤監査は残り得る。機械記録の添付が読解の手順で分かりやすいか、台帳・当番規定が無理なく読めるか、移植後の一人称と人物対応が過度な正解の先取りにならないかは、正解を知らない人によるプレイ確認が必要。人間のプレイ、自然さの採点、全シナリオの実API確認は未実施。
