# ASARIYA Codex改善指示書 v2 — 主観ログの文章生成と検証の再設計

- 作成日：2026-10-07
- 対象：https://github.com/VtuberTodoTask/obradin_like_game
- 今回の目的：大量の不採用を生む生成・検証の不整合を解消し、事実を守りながら自然な主観ログを生成する。
- 採用する方式：**AIが主観ログ全文を文章化し、本文から読み取れる意味を検証する。必須観察文の完全コピーは要求しない。**

## 0. Codexへの実行指示

本書に基づき、現在の作業ブランチの文章生成、検証、失敗診断、テンプレートへの復帰、関連するテストと文書を改修してください。原因の説明だけで終わらず、動く修正を実装してください。

前回の改善指示書にある、自動生成・事件の因果・証拠の照合・解読到達可能性・調査UIという体験上の方針は維持します。本書は文章生成と検証の具体的な実装について優先します。既に実装した全体を旧版へ戻したり、固定シナリオだけに戻したりしないこと。

最初に `AGENTS.md` があれば読み、現在のコードと失敗ログを確認すること。GitHub公開mainで確認できたコードは初回レビュー時の版であり、ユーザーが報告した `observation_changed` / `atmosphere_invalid` / `atmosphere_rejected` はその版には存在しませんでした。したがって、この指示書は新実装の根本原因を断定していません。現在の作業ブランチを調べ、推測と再現した不具合を区別してください。

現在使用しているモデル設定は維持してください。モデルを高価なものに変更すること、検査を全面的に外すこと、再試行回数だけを増やすことを主な解決策にしないこと。

## 1. 問題の切り分け

ユーザーの生成結果では、不採用の多くが次の理由でした。

> 観察本文の変更を検出した。必須観察は一字も変えず保持する必要がある。

その他は、補筆の長さ・人物名・数値・禁止語の検査、人物の状態・性質を追加したという意味検査でした。

実際のAI出力と差分が表示されていないため、現時点では次を区別できません。

| 分類 | 例 | 扱い |
|---|---|---|
| 真の意味変更 | 数値350を305へ変更、前後関係の逆転、否定の削除 | 不採用にすべき |
| 意味を保つ表現変更 | 「受付票を見た」を「受付票を確かめた」へ変更 | 原則として採用すべき |
| 変換・比較の不具合 | 別名化前の文と復元後の文を比較、人物記号の不一致 | 実装を修正すべき |
| 許可範囲の不一致 | 既存設定にある性格を検証器が禁止、台詞内の人物記号を拒否 | 入力と検査を揃えるべき |
| 情報源や視点の誤り | 見ていない操作を見たと書く、他人の内面を断定 | 不採用にすべき |
| 文章の好み | 口癖が多い、文が硬い、感情表現が単調 | 論理検査と分けて扱う |

最初に代表的な失敗を、保存された入出力で再現してください。再現用データがなければ、診断を保存する仕組みを先に入れてください。

「AIが一字でも変えた」という件数を、モデルの論理能力やストーリー整合性の失敗率として数えないこと。

## 2. 生成方式を一つに統一する

### 2.1 本番方式：全文生成と意味検証

次の流れへ統一してください。

1. プログラムが正本・知覚・必須証拠を構造化して保持。
2. AIへ、観察可能な場面と人物設定、必須証拠の意味を渡す。
3. AIが主観ログ全文を返す。
4. 本文から証拠と本文が主張する事実を抽出。
5. 必須証拠の掲載、事実の変更、無許可の証拠、視点の誤りを検証。
6. 合格した文章だけを採用。不合格の場合は具体的な問題を示して修正。
7. 修正できなければ、同じ証拠を掲載した検証済みテンプレートへ戻す。

本文全体や必須観察の文を、元の文字列と完全一致で比較して合否判定しない。構造化されたID・重要な数値・因果関係等の一致は検査する。

「自由に文章化してよい」と指示しながら「元の観察文を一字も変えるな」と検査する構成を廃止する。

### 2.2 プログラムが保持すべき情報

システム時刻、ログの持ち主、資料の種類、削除状態、人物IDと別名の対応、証拠の正本データはプログラムが保持する。AIにコピーさせて正本を再構築しない。

AIが返した本文に、本来見えていない人物のID、隠された書き手の正体、死因の正解ラベル等を混ぜない。画面上の名前への置換は、検証済みの人物参照に対してプログラムで行う。

### 2.3 固定文モードの扱い

API未設定時と復帰先としてのテンプレートモードは残す。固定の観察文に補筆を加える旧方式を残す場合は、開発用の明示的な別モードとし、本番の全文生成の検査と混在させない。

固定文モードではAIに観察文を返させず、補筆だけを返させてプログラム側で結合する。コピーの成否を検査するためのAPI呼び出しは行わない。

本改修を「固定の証明文＋短い感想」だけの実装で完了扱いにしない。全文生成でも証拠を保持できることを確認する。

## 3. 必須証拠を構造化する

自然言語の必須観察文を、そのまま全フィールドを兼ねるデータにしない。内部では少なくとも以下を区別する。

| フィールド | 内容 |
|---|---|
| `evidence_id` | 安定した証拠ID |
| `source_kind` | 直接観察、本人の記憶、発言、閲覧した文書、機械記録等 |
| `observer` | 証拠を知覚した人物 |
| `subject` / `object` | 主体・対象 |
| `predicate` | 何をした／何が記録されたか |
| `time` / `interval` | 点または区間。時刻が必要な証拠のみ |
| `value` / `unit` | 番号、測定値、単位等 |
| `polarity` | 肯定・否定 |
| `modality` | 観察、主張、推測、質問、仮定等 |
| `required_precision` | 秒分単位の時刻、単なる前後関係等、必要な精度 |
| `epistemic_scope` | その人物が直接知る範囲、文書に書いてある範囲 |
| `critical_fields` | 欠落・変更すると問題が成立しなくなる要素 |

既存のデータ形式に合わせて名称は変更してよい。一度に巨大な一般推論エンジンを作る必要はない。現在使用している証拠の型を限定的・明示的に扱う。

### 3.1 証拠とその解釈を区別する

「操作鍵350で通電したという機械記録がある」と「人物Xが故意に殺害した」は異なる情報である。前者を本文に書けば、後者まで書いたことにはしない。

「目撃者がXだと思った」という証言を、「Xが行動した」という客観的事実へ変換しない。証言の語調から客観的な真偽を決めない。

### 3.2 必須の範囲を絞る

各エントリに、そのエントリで提示する証拠だけを必須として渡す。推理の全結論や別解の一覧まで本文へ要求しない。

論理的な制約を構造化して保持することと、その制約を同じエントリで説明することは別である。

## 4. 証明文を、世界の中の証拠へ落とす

ユーザーの例に含まれる次の表現を、通常の主観ログへ定型的に繰り返さない。

- 「配給券の番号ではない」
- 「今日は手伝いではなく、登録された担当者としての作業だ」
- 「二人の受付の間に別の入居も欠番もない」
- 「医師への呼びかけではない」
- 「記録に残るのは本人が残した決意だ」

これらは別解を排除するための開発上の条件である。その条件を保証する証拠は必要だが、攻略説明として本文へ書く必要はない。

### 4.1 掲載方法の例

以下の例は方向性であり、既存シナリオで確認されていない情報を自由に追加してよいという意味ではない。正本と資料を先に整備すること。

| 内部で守りたい条件 | 世界内で示す証拠の例 |
|---|---|
| 数字は入居順 | 発行元と用途が分かる入居受付票、入居台帳の見出し |
| 作業者は登録された職能を持つ | 職場の当番記録と本人の具体的な作業、資格に関する別資料 |
| 入居の間に欠番がない | 連続した受付記録と、対象期間に欠番がないことを示す台帳 |
| 「先生」は師弟関係 | 回路の測定を教わった記憶、別人物からの同じ関係への言及 |
| 鍵に複製・貸与がない | 鍵の管理規則、受け渡し記録、対象時間の管理状況 |
| 故障を認識していた | 読んだ警告、本人の署名、復唱した具体的な内容 |
| 本人の動機・決意 | 本人の内面の記録、本人が実際に発した台詞、選択につながる行動 |

資料へ分散させた場合は、必要な資料が解読前後の適切な段階で読めることを再検証する。別解を排除する情報を単に削除しない。

### 4.2 資料の種類を使い分ける

- 主観ログ：本人が見聞きした行動・会話・感覚・内面。
- 閲覧文書の記録：書き手が読んだ台帳や点検票。その文書が主張する内容として記述。
- 機械記録：時刻、認証、測定値、信号。端末上の記録として表示。
- 会話記録：誰が何を述べたか。発言と客観的な事実を区別。

脈拍信号の停止など、意識を失った本人が知覚できない情報を、その本人の最期の独白に説明させない。機械記録や別人物が確認した証拠へ分ける。

「線量900」のような数値には、シナリオで必要な単位・測定器・基準を整備する。測定値を被曝という結論へ結び付けるゲーム内の前提がないまま、検証器だけが答えを知る構成にしない。

## 5. 生成プロンプトの契約

### 5.1 渡す情報

場面、書き手、知覚できた出来事、既知の関係・性格、許可される描写、必須証拠を渡す。

必須証拠は意味の単位で渡す。元文のコピーを要求する欄と、自然な全文を書かせる欄を併設しない。

出力はエントリIDと本文を中心とした構造化形式にする。AI自身の「守った証拠ID一覧」を合格の根拠にしない。

### 5.2 自由度を明示

**許可する内容**

- 書き手自身の感情・評価・感覚。
- 入力の人物設定に既にある性格や特徴に沿った表現。
- 証拠の条件を変えない語順変更、自然な言い換え、台詞化。
- 当該場面と整合し、推理の条件を増やさない情景描写。

**変更・追加を禁止する内容**

- 人物・所在・時刻・数量・前後・否定・行動主体の変更。
- 新しいアリバイ、道具の持ち主、接触、症状、資格、動機の確定情報。
- 書き手の知覚範囲を超えた出来事や他人の内面。
- 入力にない、人物を識別できる持続的な特徴。
- 構造化証拠では推測・主張にすぎないものの断定化。

「無口」が既存の人物設定にあるなら、それに沿う表現は許可してよい。設定にないなら持続的な特徴として勝手に追加しない。「私は口を開く気になれなかった」のような書き手自身の内面と、「相手は一言も話さなかった」という新しい出来事も区別する。

### 5.3 不要な制限の削減

人物への言及が必須の全文生成で、人物名・人物参照を一律禁止しない。既知の参照に限定して許可する。

数値が必須の証拠では、その数値を禁止語扱いしない。重要な値は一致を検査し、新しい値はその意味に応じて検査する。

感情表現や性格の描写を、一律に「観察にない新事実」として拒否しない。論理に影響する追加と、許可された描写を分類する。

長さは目安とする。少し長い、短いという理由で、証拠が正しく掲載された本文を論理不合格にしない。極端な長さは別の品質項目として扱う。

## 6. 人物参照と正規化

人物参照は、内部ID、AIに渡す別名、画面用の暗号、解読後の名前を区別する。

処理順を明示し、同じ段階で比較すること。

1. 正本は内部IDで保持。
2. リクエストごとに安定した別名へ変換してAIへ渡す。
3. 出力中の参照を検査。未知の参照や解釈不能な参照はエラー。
4. 既知の参照を内部IDへ戻す。
5. 証拠の抽出・照合を、対応が揃った形式で行う。
6. 採用本文を保存し、表示時にプレイヤーの解読状態を反映。

マスク後の文字列と別名化前の本文を、直接比較しない。ログの持ち主と実際の書き手が異なる移植ケースでも、書き手の正体を本文へ漏らさない。

句読点や空白の正規化は必要な範囲で行うが、否定、数値、時刻、人物、大小関係まで消して一致扱いにしない。すべての数字を除去するような正規化は禁止。

## 7. 意味検証を実装する

### 7.1 構造・形式の検査

JSON形式、エントリID、空本文、未知人物参照、伏せるべきIDの露出等はプログラムで検査する。これらと文章の意味の誤りを別集計にする。

### 7.2 本文からの抽出

抽出処理は、本文が明示している内容を、主体・対象・行動・時刻・値・否定・主張の種類として返す。各抽出には、その根拠となる本文の引用箇所を添える。

抽出器へ「正解の証拠一覧」を渡し、その一覧をそのまま返させない。本文、参照対応、限定した証拠の語彙、読解に必要な文脈を渡し、期待値との比較は後段で行う。

引用箇所は実際の本文に存在することをプログラムで検査する。ただし、存在する引用が付けば意味が正しいという保証にはならない。引用と抽出内容が結び付いているかも検証する。

曖昧な代名詞で主体を確定できない、数値の対象が分からない等は、読み取り不能として扱う。正本の真相で補完しない。

### 7.3 必須証拠との比較

比較は証拠の型ごとのルールで行う。

| 要素 | 検査の例 |
|---|---|
| 人物 | 行動主体・対象・主張者が同一か |
| 数値 | 必要な番号・値・単位が一致するか |
| 時刻 | 証拠が要求する精度を満たすか |
| 順序 | 入居前後、操作と死亡の前後が保持されているか |
| 否定 | 「貸していない」「知らない」等が保持されているか |
| 範囲 | 指定した期間だけの事実を、生涯の事実へ拡張していないか |
| 情報源 | 本人が見たことか、文書にあることか、他人が述べたことか |
| 主張の種類 | 推測を断定へ、引用発言を客観的事実へ変えていないか |

例：「入居時の受付票には三番とあった」と「入居時に渡された受付票を見た。入居順は3番」は、受付票の用途と数字の関係が文脈で明白なら同じ証拠として採用する。

一方、「配給券には三番とあった」への変更は証拠の対象を変えているため拒否する。

### 7.4 指定外の情報

追加された事実を次の三つに分類する。

1. **正本や既存設定にあり、書き手が知覚可能な情報**：原則許可。新しい証拠として使う場合は、解読の順序や答えの漏洩が変わらないか確認。
2. **感情・評価・証拠に影響しない描写**：許可範囲に沿って採用。
3. **正本にない行動や、推理条件を変える特徴・所在・数量等**：不採用。

真相と合っていても、書き手には知り得ない追加は許可しない。検証器だけが知る正解を、AIの偶然の追加で開示させない。

### 7.5 検査の限界

自由文の意味検証は完全な数学的保証ではない。決定的な検査、LLMによる抽出・意味判定、人が見る品質確認を区別して報告する。

LLM検証の曖昧な指摘だけで、同じエントリを無制限に再生成しない。まず具体的な引用と変更された要素を示させる。根拠のない指摘は「検証の不確実性」として扱い、勝手に採用することも、作者の設定を変更することもしない。解消できなければ検証済みテンプレートへ戻す。

## 8. 失敗診断を具体化する

現在の `observation_changed` は、全文一致を要求する不採用コードとして使わない。移行後は次のような意味の異なる理由へ分類する。

- `missing_required_evidence`：必要な証拠が本文から読めない。
- `changed_subject` / `changed_object`：主体・対象が変わった。
- `changed_value` / `changed_time`：重要な値・時刻が変わった。
- `reversed_order`：前後が逆。
- `lost_negation`：否定が失われた。
- `changed_source` / `changed_modality`：情報源・推測の扱いが変わった。
- `unauthorized_event` / `unauthorized_trait`：新しい出来事・特徴を追加。
- `viewpoint_violation`：知覚できない内容を記述。
- `reference_mapping_error`：別名・人物参照の変換問題。
- `verification_uncertain`：検証結果を確定できない。
- `quality_warning`：論理上の不合格ではない文章品質の問題。

`atmosphere_invalid` のような複数条件をまとめたコードも分解する。表現や長さの問題を、事実変更と同じ集計へ入れない。

開発用パネルとJSON出力で、次を確認可能にする。

- シード、生成版、プロンプト版、モデル、場面ID、エントリID。
- 実際に送った生成入力と返った本文。
- 必須証拠の構造、抽出結果、根拠の本文箇所。
- どのフィールドが、期待値から何へ変わったか。
- 別名化・復元の対応と処理段階。
- 各修正試行の結果、最終的に使った本文の由来。

APIキー等の認証情報は保存・表示しない。開発用の真相・対応表は、プレイ画面へ出さない。

診断例：

> 不採用：`changed_value`。鍵番号の期待値は350、本文は305。該当文：「操作鍵305で遮断を解除した」。人物と時刻の抽出は一致。

この粒度でAIへ修正指示を返し、単に「観察を変えるな」と繰り返さない。

## 9. 再試行と復帰

最初の出力が不合格なら、問題のあるエントリだけを修正する。同じ場面に複数の記録がある場合は、既に合格した記録と確定した場面の内容も参照させる。

修正回数の初期値は2回とする。設定可能にするが、回数の増加を修正の代わりにしない。

修正入力には、前の本文、具体的な変更箇所、守るべき意味、許可される言い換えを渡す。変更した本文を再検査し、差分が小さいという理由で無条件に通さない。

同じ失敗が続いた場合、以下を区別する。

- 元の場面・証拠に矛盾や不可能な視点がある：前提の問題。
- 証拠は成立するが、本文が繰り返し変更する：生成の問題。
- 正しい意味の本文を検証器が拒否する：検証の問題。
- 人物対応や比較段階が違う：実装の問題。

同じコードが2回続いたという理由だけで「仕様エラー」と断定しない。

解消できなければ、同じ証拠を掲載し、検証に通ったテンプレートへ戻す。復帰した件数と理由を記録し、シナリオ全体を生成し直さない。変更した記事に依存する後続の文章・キャッシュは再検証する。

## 10. テンプレートとキャッシュ

テンプレートは、必須証拠を含む自然な資料として作る。別解排除の説明文を連結するだけの出力を復帰先にしない。

テンプレート本文にも証拠掲載の検査を適用し、本文を削ったのに内部の事実IDだけでPASSする処理を残さない。

生成形式、証拠モデル、人物対応、プロンプト、検証ルールの更新に合わせてキャッシュの版を更新する。シードとモデルだけの一致で、異なる版の本文を再利用しない。証拠・入力の変更もキャッシュ無効化へ反映する。

診断データの再検査は、保存済み本文を使って実施できるようにする。検証器を直すたびに生成APIを呼び直す必要がない構成にする。

## 11. 回帰テスト

少なくとも以下を、API不要の保存済みサンプルまたはスタブで確認する。

### 採用されるべき例

1. 語順変更・句読点変更・自然な同義表現で、必要な意味が同じ。
2. 「3」と「三」、時刻表記の違い等が、必要な精度を保っている。
3. 既存設定にある特徴を記述。
4. 書き手自身の感情を追加。
5. 別名の復元前後で同じ人物を正しく照合。
6. 文書を読んだことを、文書の主張として正しく表現。

### 拒否されるべき例

1. 鍵番号350を305へ変更。
2. 入居の前後、行動主体・対象を逆にする。
3. 「貸していない」を「貸した」へ変更。
4. 推測を確定事実へ変える。
5. 他人の目的を、知覚した根拠なく断定。
6. 未知人物、重要な新しい道具、識別用の新特徴、存在しないアリバイを追加。
7. 時刻の重要な区間を落とす、期間限定の事実を常時の事実へ変える。
8. 本文を「眠い。」へ置換し、内部の証拠IDだけを残す。
9. 本人が知覚していない死後の確認や機械情報を、本人の経験として記述。

### 工程・報告の確認

1. 修正時の指摘に具体的な要素と本文箇所がある。
2. 保存された正しい本文を、検証器の修正だけで再採用できる。
3. テンプレート復帰で証拠・到達可能性が維持される。
4. 版の異なるキャッシュが混ざらない。
5. プレイ画面のマスク解除前に、診断用の真相や参照対応が漏れない。

意味抽出をスタブで行うテストは、照合処理のテストとして明記する。実際のAI抽出の信頼性を確認したテストと数えない。

## 12. 実装順序と検証の規模

1. 現在の失敗を保存・再現できる診断を実装。
2. 完全一致検査と自由な全文生成の混在を解消。
3. 証拠の構造、人物参照、意味の照合を実装。
4. 前提の説明文を、正本と世界内の資料へ分ける。
5. 生成・抽出プロンプトと具体的な修正指示を更新。
6. 保存済みサンプルとスタブによる回帰テスト。
7. 現在のモデルで小規模に実生成し、誤検知と本当の意味変更を分類。
8. テンプレート復帰、キャッシュ、文書、開発用レポートを更新。

APIテストは既存の設定・実行方針の範囲で行う。まず代表的なエントリ10件程度で確認し、未解決の不具合があるまま大量生成しない。APIキーがなければAPI不要部分を完了し、実API検証は未実施と明記する。

小規模確認が通ったら、代表的な固定シナリオ1本とランダムシナリオ3本程度を確認する。実際に生成した全エントリを母数にし、都合のよい成功例だけを報告しない。

## 13. 報告する指標

次を分けて集計する。

| 指標 | 定義 |
|---|---|
| 初回採用率 | 修正なしで採用された全文／初回生成した全文 |
| 修正後採用率 | 修正を含め採用されたLLM全文／対象全文 |
| テンプレート復帰率 | テンプレートへ戻した全文／対象全文 |
| 真の意味変更 | 人が確認しても必要な証拠が変更・欠落した件数 |
| 誤検知 | 必要な意味が保持されているのに拒否した件数 |
| 検証不確実 | 検証結果を確定できず復帰等にした件数 |
| 品質上の問題 | 論理上は正しいが、硬さ・反復・説明過多等がある件数 |
| 費用と回数 | 生成・抽出・修正の呼び出し数と、利用可能ならトークン数 |

同じエントリを3回拒否した場合、3件の異なるシナリオ不具合として数えない。エントリ単位と呼び出し単位を別に示す。

人による判断を実施していないものは、「真の意味変更」「誤検知」の確定値にしない。自動判定の分類として報告する。

合格率だけで改善を判断しない。誤った証拠を通した例がないかと、自然な文章が通るかを両方確認する。

## 14. 完了条件

- 現在の作業ブランチで代表的な失敗を再現し、原因を生成・検証・変換・前提へ分類できる。
- 全文生成で必須観察文の完全コピーを要求していない。
- 同じ意味の言い換えは通り、重要な意味変更は拒否される回帰テストがある。
- 未掲載の証拠を、内部事実IDだけで掲載済みと判定しない。
- 「人物名・数値・禁止語・長さ」の一括拒否をやめ、理由と該当箇所が分かる。
- 発言・推測・直接観察・機械記録を混同しない。
- 主観ログへ解法や別解排除の説明を列挙せず、必要な条件は世界内の証拠として提示される。
- 証拠を分散した後も、解読到達可能性と一意性が維持される。
- 現在のモデル設定で確認できる。高価なモデルへの変更を完了条件にしていない。
- API未設定でも検証済みテンプレートで遊べ、不採用からの復帰が可能。
- 生成版・プロンプト・証拠・検証版が診断とキャッシュに反映される。
- 実API検証を行ったかどうか、その範囲と未確認事項が明記される。

## 15. 最後に提出する内容

1. 大量不採用のうち、何が実装の問題で、何がAIの事実変更だったか。未判明のものは区別する。
2. 新しい生成・検証・修正・復帰の流れ。
3. ユーザーの失敗例に対応する、生成前後の具体例を3件以上。本文、証拠の構造、抽出結果、採用／拒否理由を示す。
4. 回帰テストの結果と、実API検証の有無・規模。
5. 初回採用、修正後採用、テンプレート復帰、誤検知、未確定の分類。
6. 主観ログとしての自然さと、別解排除に必要な証拠が両立している例。
7. 残る限界と、人間のプレイ確認が必要な箇所。

「検査を緩めたので採用率が上がった」「再試行で通るまで回した」だけでは完了ではありません。自然な言い換えを許し、重要な事実の変更を検出できる状態にしてください。
