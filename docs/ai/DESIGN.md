# シェルター推理ゲーム 自動生成システム 設計書 v2

- 更新日：2026-10-07
- 現行の改修方針：[FIXES.md](FIXES.md)。以下のv2設計が旧版の規模・生成順序・警戒度・検証方式に優先する。

## v2の中心体験

身元を知ると新しい記録が開き、以前の「安全を保証した発言」や「確信した目撃」の読み方が変わる。資料の出典・時刻・観察範囲を比較し、行動を結果へ結び付ける。名前の置換だけで解読の価値を終わらせない。

## v2の生成と因果

住人・関係を生成し、事件の型が必要とする専任職能を確保する。目的と対立、道具・資格・知識の前提、具体的な行動、その結果としての死亡、各人物の観察と主張、解読の経路の順に構成する。死亡時刻と死因を先に抽選して中心事件を後付けしない。

事件は `objectives / participants / actions / consequences / downstream` を持つ。行動の `causes` は断線の認識→通電、投与→摘出、入場→襲撃など内容のある参照。結果は原因行動のIDに接続する。所持区間、専任権限、死後の行動、未来の観察、結果との一致を検査する。

三種類の構造を使う。設備型は断線の警告、専用鍵、匿名の通電、身体の感電を結ぶ。配給型は受領の不一致という対立、継続所持の手袋、両腕の接触と転落を結ぶ。身元型は薬剤の上限、警告を読んだ意図的な増量、投与と身体の停止、別の身体での同一チップの更新を結ぶ。動機だけで加害者を確定しない。

補助事件も個人の接触・検査・発症・死亡を保持する。架空病Kは接触後三日で検査、症状を経て死亡。飢餓は個人への配達停止から21日以上の消耗を置き、倉庫在庫と個人の受領量を区別する。事故の反復は同じ梁が一度に崩れる共同救助として説明する。

## v2の証拠と公平性

観察本文は対象、操作番号、時刻・区間、否定、前後関係、観察範囲を含む。発言と実測を別の型として表し、「そう語った」と「客観的に正しい」を混同しない。暗い輪郭の確信した証言には、連続映像の所在という検証手段を置く。弱い正証言にも道具と操作による照合手段を置く。

限定されたテンプレート本文を独立に抽出し、読み戻した観察だけで推論する。内部の `facts / rendered / writer / certainty` を正答の根拠に使わない。真相は整合性検査と最後の照合にのみ使う。同じ観察のコピーで確信度を加算する方式は採らない。

身元の区画・入居順・職能をCSPで解き、読める資料と事件の部分的結論を各段で記録する。匿名の操作に記録された専任資格を、継続した道具の所持へ結ぶと職能が分かる。その身元の解読で、故障への認識や投与量の知識を確かめる。未解読本人の入口証拠を先取りしない。

文化の仮説は区画・職能分類・入居帯という有限集合と、各印への全単射。既知人物の比較から矛盾する候補を排除する。複数候補が同じ区画を与える部分だけは利用できる。正解の文化表を選択に使わない。「支給品と受付の規定」は世界内の文書として概要に置き、正解の対応表を表示しない。

## v2のプレイと規模

標準8〜10人、相談役2人、主観ログ35〜55件を調整目標とする。12〜16人版も同じ検証を使う。各ログに身元、事件、関係、再解釈、経過の役割を持たせる。1件60〜180字を目安にし、必要な因果のための長短は許容する。目標を理由に証拠を削らない。

仮の名前・身元候補・生死候補・根拠・ピン・2資料比較・時系列を保存する。標準の上限時は認証の一時停止と再接続。ハードは旧接続遮断。身元の採点は従来のID解読を使い、選択人物の候補との対応違いは通知する。途中確認は解読済みの正しい3人分をまとめて確定し、未知の加害者を開示しない。

安全判定は既存の「危険＞価値なし＞安全」と潜伏者・感染・汚染・侵入者の集合を維持する。死因の危険が早く見えても、加害者の現在の身体、生存者、侵入者の退場を確かめる理由を残す。

## v2の文章化・検証と限界

真相の整合性、閲覧可能な証拠からの到達・一意性、本文の掲載を別々に報告する。身元、身体の生死、死因、加害者、安全判定に出典付きの導出経路を出す。本文を「眠い。」に置換する回帰試験と、証拠を実際に除去する反例試験を必須にする。

v2.1ではLLMに限定した型の意味契約、人物の設定、前の経過と観察範囲を渡し、主観ログ全文を生成する。完成文の完全コピーは要求しない。抽出器には期待する証拠一覧を渡さず、本文・参照・語彙から読み取った内容と引用を返させる。別の監査と決定的なフィールド比較で掲載・変更・追加を判定し、問題のあるエントリだけ修正する。修正は既定2回、失敗は同じ証拠の検証済みテンプレートへ戻す。感情・既存設定の表現と品質警告を論理不合格から分ける。

受付票・連続した台帳・当番規定は世界内資料として提示する。自己の最期の感覚と、医療端末の脈拍信号停止の自動付記を分離する。線量には単位と架空世界の判定基準を付ける。本文・期待値・抽出・引用・修正履歴を開発用に保存し、保存本文を再生成せずに再検査できる。キャッシュは本文・意味契約・前の経過・モデル・プロンプト・検証版へ結び付ける。

現在は三つの小さな事件の型であり、人物配置・支給印の系統・解読順序に反復がある。生活全体や任意の物理過程をシミュレーションしてはいない。全文の意味抽出・監査はLLM判断を含む。決定的な照合テスト、実APIの小規模確認、人間の未実施の確認を [NARRATION.md](NARRATION.md) で分けて報告する。

## 1. 概要

Return of the Obra Dinn、Type Help などに代表される「資料を読み解いて人物の身元と死因を特定する」推理ゲームを、**シナリオ自動生成**で無限に遊べるようにする。

最大の設計方針は次のとおり。

- **論理層と物語層を分離する。**
  - 論理層（真相・手がかり・検証）はプログラムとソルバーで生成・検証する。
  - 物語層（ログの文章）だけを LLM が担当する。
- **LLM に論理を考えさせない。** LLM は「決定済みの事実を、指定された人物の主観の文章に変換する」ことだけを行う。
- 生成されたシナリオは、**到達可能性**（詰みがない）と**一意性**（解が一つに定まる）の両方を機械的に検証してから出力する。

## 2. 世界観とゲームの目的（決定）

### 2.1 世界観
- ポストアポカリプスの世界。人々は地下シェルターで暮らしている。
- 各シェルターには、住人のデータ（健康管理・人間関係など）を保存する**管理AI**がある。
- 住人の脳内には**チップ**が埋め込まれており、死ぬまでの**主観的な体験を、感情に基づいて文章化したログ**として管理AIに保存し続ける。
- 管理AIは原則として住人に干渉しない。
- 各シェルターには複数人の**相談役**がいる。相談役だけが管理AIと対話でき、AIと相談してシェルターの方針を決める。

### 2.2 プレイヤー
- 物資を漁る**漁り屋**。ハッカー技能を持ち、シェルターの管理AIからデータを抜き出すことができる。
- 連絡が途絶えたシェルターの管理AIからデータを抜き出し、**そのシェルターが探索するのに安全かどうか**を判定する。

### 2.3 ゲームの目的
プレイヤーは以下をすべて特定し、最後に安全判定を下す。
1. 全住人の身元（ID と名前の対応）
2. 死者それぞれの死因（および加害者がいればその人物）
3. 生存者の有無
4. シェルターの安全判定（§7）

## 4. ID システム（決定）

### 4.1 形式
```
区画 - 入居順 - 職能コード
例：C-07-31
```

| 要素 | 形式 | 説明 |
|---|---|---|
| 区画 | アルファベット1文字（A〜D） | 住人が暮らす区画。記号として使うだけで英語力は不要 |
| 入居順 | 2桁の数字（01〜） | **シェルター全体での通し番号**。欠番がありうる（§9 トリック4） |
| 職能コード | 2桁の数字 | 下の職能コード表による |

- 英単語の略称（MED など）は使わない。プレイヤーの英語力に依存させないため。
- **職能コード表はゲーム開始時から資料として参照可能**とする。

### 4.2 職能コード表

| コード | 分類 | 職能 |
|---|---|---|
| 11 | 医療 | 医師 |
| 12 | 医療 | 看護 |
| 13 | 医療 | 薬剤管理 |
| 21 | 食料 | 農耕 |
| 22 | 食料 | 調理 |
| 23 | 食料 | 配給管理 |
| 31 | 設備 | 電気 |
| 32 | 設備 | 空調・浄水 |
| 33 | 設備 | 修繕 |
| 41 | 保安 | 警備 |
| 42 | 保安 | 外部偵察 |
| 51 | 管理 | 相談役 |
| 52 | 管理 | 記録係 |

- 同じ職能を複数人が持ちうる（例：農耕が3人）。職能だけでは個人を特定できないようにするため。
- 職能コード表は将来の拡張に備えて設定ファイル（JSON/YAML）で定義すること。

### 4.3 推理上の役割
ID の3要素はそれぞれ異なる種類の推理に対応する。
- **区画**：位置の推理（移動の描写などから読む）
- **入居順**：時系列の推理（「あの人は私より後に来た」などの記述から読む）
- **職能**：行動の推理（仕事内容の描写から読む）

## 5. 資料（ログ）と解錠の仕組み（決定）

### 5.1 資料の種類

| 資料 | 内容 | 初期状態 |
|---|---|---|
| 職能コード表 | §4.2 の表 | 最初から閲覧可能 |
| 相談役の会話ログ | 相談役と管理AIの対話記録。方針決定の経緯を含む | 最初から閲覧可能 |
| 主観ログ | 各住人の脳内チップの記録。本人の主観・感情に基づく文章 | 本人の ID を入力すると閲覧可能 |

- **ゲーム開始時は相談役（職能51）の ID だけが平文で判明している**（暫定：相談役全員）。そこを入口に推理を進める。

### 5.2 伏せ字（マスク）の仕組み
- 管理AIはログを文章化するとき、**人物名を ID に置き換えて保存している**。
- プレイヤーがまだ解読していない ID は、ログ中で**伏せ字**として表示される。
- 伏せ字は**人物ごとに一貫した暗号文字列**で表示する（暫定）。
  - 例：`[⟨x9Kq⟩]` のように、同じ人物は常に同じ暗号文字列で表示される。
  - これによりプレイヤーは「別々のログに出てくる同じ伏せ字は同一人物」と追跡できる。
- ID を正しく解読すると、**全ログの該当する伏せ字が一斉に名前に置き換わる**。

### 5.3 解錠（Type Help 型の仕組み）
- プレイヤーは ID を入力する。正しい ID であれば、その人物の主観ログが開き、伏せ字が解除される。
- **誤った ID を入力すると、管理AIの侵入検知の「警戒度」が上がる**（暫定）。警戒度が上限に達した場合の扱いは §14 を参照。
- 総当たりを実質的に不可能にするのが警戒度の目的。

### 5.4 ログのデータ構造（暫定）
各主観ログはエントリの列で構成される。

| フィールド | 説明 |
|---|---|
| `owner_id` | ログの持ち主の ID |
| `timestamp` | 管理AIが付与するシステム時刻（日数＋時刻）。メタデータとして表示される |
| `emotion` | 主な感情（恐怖・怒り・安堵など）。表示するかは UI 次第 |
| `text` | 主観の文章。他人への言及は ID トークン（後述）で表現 |

- **場所はメタデータに含めない**（暫定）。場所は本文の描写から読み取らせる。
- **死者のログの最後のエントリは、死の直前の主観**（感覚・感情）とする。死因の主要な手がかりになる。
- **生存者のログは現在まで更新され続けている**。「最終更新日時が新しいログがある」こと自体が生存者の手がかりになる。

## 6. 生成パイプライン（決定）

```
[1] 住人の生成
[2] 関係の生成
[3] 事件の生成（トリックの適用）
[4] 現在の状態の決定 → 安全判定の導出
[5] 出来事と認識の生成
[6] 解錠グラフの設計 ＋ 到達可能性の検証
[7] 一意性の検証
      ↑ 失敗したら手がかりを調整して [3]〜[6] を再試行
[8] 文章化（LLM）＋ 往復検証
[9] シナリオ出力（JSON）
```

**[1]〜[7] はプログラムとソルバーで行う。LLM を使うのは [8] のみ。**

### 6.1 [1] 住人の生成
- 人数・区画数を決め、各住人に区画・入居順・職能を割り当てて ID を作る。
- 名前、年齢、性格傾向、話し方の特徴（文章化の際の文体指定に使う）を付与する。
- 相談役（51）を 2〜3 人含める。

### 6.2 [2] 関係の生成
- 住人間の関係を生成する（家族、友人、恋人、対立、師弟など）。
- 関係は2種類に分けて持つ。
  - **管理AIが把握している関係**：接触の多さから AI が推定したもの。資料として抜き出せる（§14 参照：資料化するかは未決定）。
  - **隠れた関係**：AI が把握していない関係（秘密の恋愛、表向きは友好的だが実際は対立など）。トリックや動機の材料になる。

### 6.3 [3] 事件の生成
- §9 のトリックテンプレートから 0〜2 個を選んで適用する（暫定）。
- 死者・死因・加害者・死亡時刻・死亡場所を決める。
- 死因の種類（暫定）：殺人、感染症、被曝、飢餓、事故、侵入者による殺害。

### 6.4 [4] 現在の状態の決定
以下を決め、§7 のルールで安全判定を導出する。
- 生存者（0〜2人）とその所在・状態
- 加害者が生存して潜伏しているか
- 感染・汚染・侵入者など、残っている危険
- 物資の残量

### 6.5 [5] 出来事と認識の生成
事件の時系列を「場面」の列として生成する。各場面について：
- **真の出来事**（何が起きたか）
- **各人物の認識**（その場にいた人物が何を見聞きし、どう解釈し、どう感じたか）
  - 認識は誤っていてもよい（§9 トリック3）
  - その場にいなかった人物は記録しない

### 6.6 [6] 解錠グラフと到達可能性
- 各ログのどこに、どの人物の ID の手がかり（区画・入居順・職能）を置くかを設計する。
- **到達可能性の検証**（§8.2）を行い、初期状態から全員の ID に到達できることを保証する。

### 6.7 [7] 一意性の検証
- 全ログを開いた状態で、身元・死因・安全判定が一意に定まることをソルバーで検証する（§8.3）。
- 解が複数ある → 手がかりを追加する。
- 推理が簡単すぎる（暫定の指標：§8.4）→ 手がかりを削る。

### 6.8 [8] 文章化（LLM）
§10 を参照。

## 7. 安全判定（決定）

### 7.1 選択肢
- **安全**
- **危険（理由）**
- **価値なし**

### 7.2 判定ルール

| 状況 | 判定 |
|---|---|
| 身内同士の殺し合いで、全員死亡または生存者に加害者がいない | 安全 |
| 身内同士の殺し合いで、加害者が生存して潜伏している | 危険（潜伏者） |
| 感染症 | 危険（感染） |
| 被曝 | 危険（汚染） |
| 侵入者が中に残っている | 危険（侵入者） |
| 飢餓 | 価値なし |

### 7.3 優先順位
死因が混在する場合は、次の優先順位で判定する。

**危険 ＞ 価値なし ＞ 安全**

- 一つでも危険が残っていれば「危険」
- 危険がなく、物資が尽きていれば「価値なし」
- どちらでもなければ「安全」
- 危険の理由が複数ある場合は、すべて列挙する（暫定）

## 8. 検証（ソルバー）

### 8.1 手がかりの形式化
検証は文章ではなく、**構造化された「手がかり事実」**に対して行う。ログの文章は [8] で手がかり事実から生成される。

手がかり事実の型（暫定。実装時に拡張してよい）：

| 型 | 例 |
|---|---|
| `DISTRICT(p, d)` | 人物 p は区画 d に住む |
| `JOB(p, j)` | 人物 p の職能は j |
| `JOB_CATEGORY(p, c)` | 人物 p の職能は分類 c（医療など）に属する |
| `ENTERED_BEFORE(p, q)` | p は q より先に入居した |
| `ENTRY_ORDER(p, n)` | p の入居順は n |
| `SAME_PLACE(p, q, t)` | p と q は時刻 t に同じ場所にいた |
| `RELATION(p, q, r)` | p と q の関係は r |
| `DEATH_SIGN(p, s)` | p の最期に感覚 s があった（死因の手がかり） |
| `ALIVE_AT(p, t)` | p は時刻 t に生きていた |
| `NOT(...)` | 否定 |

- 手がかり事実の主語 p は、ログ中の伏せ字（人物トークン）を指す。
- 各手がかり事実は、**どのログのどのエントリに含まれるか**を持つ。

### 8.2 到達可能性の検証
プレイヤーの推理を模擬する。

```
既知ID = 相談役のID
ループ:
  読めるログ = 既知IDのログ ＋ 初期資料
  読める手がかり事実を集める
  未解読の各人物トークンについて:
    制約（読める手がかり事実＋ID形式＋職能コード表）のもとで
    その人物の区画・入居順・職能がすべて一意に定まるか、ソルバーで確認
    定まれば 既知ID に追加
  新しく追加された ID がなければ終了
全員の ID が既知IDに含まれていれば「到達可能」
```

- ソルバーは制約充足ソルバー（例：Python の OR-Tools CP-SAT または Z3）を推奨。
- 一意性の確認は「解を一つ求め、その解を禁止する制約を加えて再度解き、解がなければ一意」という標準的な手法でよい。

### 8.3 一意性の検証
全ログを読める状態で、以下がすべて一意に定まることを確認する。
- 全人物トークンと ID の対応
- 死者それぞれの死因と加害者
- 生存者の集合
- 安全判定

### 8.4 難易度の指標（暫定）
- 到達可能性の検証ループの**反復回数**（推理の段数）
- 各段で新たに解読できる ID の数（一度に大量に解ける段は簡単すぎる）
- 試作では指標を記録・出力するだけにとどめ、調整は後回しでよい。

## 9. トリックテンプレート（決定：試作は5種）

| # | トリック | 内容 | 見抜く手がかり | 安全判定への影響 |
|---|---|---|---|---|
| 1 | チップの移植 | 死者のチップを別人に移し、身元を偽装する | ログの途中で語り口・感情の傾向が変わる | 加害者が生存していれば危険 |
| 2 | ログの改ざん | 相談役が管理AIに記録の削除・修正を依頼する | 相談役の会話ログと、他の住人のログの矛盾 | 隠された死因次第 |
| 3 | 主観の誤認 | 暗闇や混乱の中で、人違いや状況の勘違いをしている | 同じ場面を記録した別の人物のログとの食い違い | 直接は影響しない |
| 4 | 記録にない人物 | チップを持たない侵入者、または記録から消された住人 | 入居順の欠番、ログ中の正体不明の存在 | 侵入者が残っていれば危険 |
| 5 | 死因の偽装 | 殺人を事故や感染症に見せかける | 本人の最期の感覚と、公式の記録が合わない | 見抜ければ判定が変わる（例：感染→安全） |

### 実装上の要件
- トリックは**プラグイン形式**で実装し、テンプレートを後から追加できるようにする。
- 各テンプレートは以下を定義する。
  - 適用条件（例：トリック2は相談役が生存または死亡前に関与できること）
  - 真相データへの変更内容
  - 必ず生成すべき手がかり事実（見抜くための手がかり）
  - 安全判定への影響
- トリックによって生じる「偽の事実」（改ざんされた記録、誤認）は、真の事実と区別してデータに持つこと。ソルバーは偽の事実を「そう記録されている」ものとして扱い、真相とは別に検証する。

## 10. 文章化（LLM）

### 10.1 役割
LLM は [5] で生成した「各人物の認識」と、そのエントリに含めるべき手がかり事実を受け取り、**その人物の主観ログの文章**を出力する。

### 10.2 入力（暫定）
- 書き手の人物プロフィール（名前、性格傾向、話し方の特徴）
- 場面の認識データ（何を見聞きし、どう解釈し、どう感じたか）
- **必ず含める手がかり事実**のリスト
- **書いてはいけない事実**のリスト（その人物が知らないこと、答えに直結しすぎる情報）
- 世界観の語彙（§4.2 の職能、区画名など）

### 10.3 出力の制約
- 他の人物への言及は、名前ではなく**人物トークン**（例：`{P:C-07-31}`）で書く。表示時にゲーム側が名前または伏せ字に置き換える。
- 書き手本人の名前や ID を本文に書かない。
- 出力は JSON（構造化出力）で受け取る。

### 10.4 往復検証
LLM の出力は、書き漏らしや書きすぎが起きうるため、必ず検証する。
1. 生成された文章を、**別の LLM 呼び出し**で読ませ、含まれている事実を手がかり事実の形式で抽出する。
2. 抽出結果を、意図した手がかり事実の集合と照合する。
   - 必須の事実が欠けている → 再生成
   - 書いてはいけない事実が含まれている → 再生成
3. 一定回数（暫定：3回）失敗した場合は、そのシナリオを破棄して [3] からやり直す。

### 10.5 LLM の呼び出し
- LLM のプロバイダとモデルは設定で差し替え可能にする（API とローカル LLM の両方を想定）。

## 12. 試作（MVP）の範囲

### 12.1 作るもの
1. **シナリオ生成器**：シード値を指定して、§6 のパイプラインでシナリオ JSON を生成する。同じシードで同じ結果が再現できること（LLM 部分を除く）。
2. **検証器**：シナリオ JSON を読み込み、到達可能性と一意性を検証してレポートを出す。
3. **最小限のプレイ用 UI**：ターミナル（CLI）またはシンプルな Web 画面で以下ができること。
   - 閲覧可能な資料の一覧表示と閲覧
   - ID の入力と解錠（伏せ字の一斉解除）
   - 警戒度の表示
   - 最終回答（身元・死因・安全判定）の提出と正誤判定

### 12.2 推奨する技術構成（暫定）
- 言語：Python
- ソルバー：OR-Tools（CP-SAT）または Z3
- LLM：構造化出力（JSON）に対応した API。プロバイダは差し替え可能に
- 設定（職能コード表、トリック、確率など）は外部ファイルで管理

### 12.3 完了条件
- 異なるシードで 20 本以上のシナリオを生成し、すべてが到達可能性と一意性の検証を通過する。
- 生成された文章が往復検証を通過する。
- プレイ用 UI で、生成されたシナリオを最初から最後まで遊べる。

### 12.4 作らないもの（試作の範囲外）
- グラフィック、音声
- キャラバン型など、シェルター以外の舞台
- 難易度の自動調整（指標の記録のみ行う）
